# 业务架构与系统分层

本页把两件事分开说明：**业务架构**回答谁通过哪些模块完成经营闭环；**技术架构**回答这些能力由哪些程序与数据层承载。支付、退款、结算的时序在对应模块中单独展开。

## 1. 业务架构

GOEPAY 围绕商户经营与资金闭环组织功能。管理员配置经营规则并处理运营事务；商户完成接入、收款和售后；付款用户在支付机构确认付款。模块之间通过原业务号、权限与账务记录衔接。

<Diagram name="business-architecture" caption="GOEPAY 业务架构：角色、经营配置、交易资金与运营服务" />

| 业务层 | 主要模块 | 交付的业务结果 |
| --- | --- | --- |
| 经营配置 | 商户、用户组、支付方式、通道、轮询与费率 | 确定谁能用什么产品、按什么规则收款 |
| 交易处理 | 收款、订单、原单查询、回调与商户通知 | 确认可核实的交易结果并同步商户业务系统 |
| 资金处理 | 余额、退款、结算、代付、分账与保证金 | 以原业务号核对预占、确认扣减与释放 |
| 运营服务 | 实名认证、OCR、消息、打印、投诉与进件资料 | 完成辅助服务及机构协作所需流程 |
| 平台治理 | 权限、风控、统计、公告、任务、日志与维护 | 保留可追踪的政策、审计及运营结果 |

业务图中的关系表示职责与协作，不代表所有模块都已开通外部产品。尤其是本地进件审批与机构真实进件、投诉回复与机构关闭、OCR 与实名认证，必须区分。

## 2. 从模块看一次业务闭环

| 阶段 | 管理员 | 普通商户 | 关联记录 |
| --- | --- | --- | --- |
| 开通 | 配置通道和用户组，创建商户 | 本人登录，核对通道及接入资料 | 商户号、用户组、授权通道 |
| 收款 | 查看订单和异常，核对原通道 | 接入收款、查看订单与通知结果 | 商户订单号、平台订单号、机构交易号 |
| 售后 | 处理获准退款与资金限制 | 从原订单申请退款 | 原退款号、退款状态、资金明细 |
| 结算 | 审批并按授权执行付款 | 维护结算账户、提交申请 | 结算申请、原付款、预占与费用 |
| 日终核对 | 报表、日志、资金记录交叉核对 | 核对自己的收入、退款、提现 | 同一口径的原业务记录 |

## 4. 技术架构

后台与收银台负责交互，Go API 负责身份、政策和业务事务，PostgreSQL 保存订单、账务与持久任务。Worker 和调度执行既有授权范围内的异步工作。商户系统和支付机构分别通过签名请求、可信回调与通知协议连接。

<Diagram name="system-architecture" caption="GOEPAY 技术架构：接入、Go 业务模块、任务处理与数据层" />

核心任务可由 PostgreSQL 持久保存；图中不额外假设已部署 Redis 或其它消息队列。后台配置保存、计划授权和实际执行仍是不同环节。

## 5. 历史业务保持原身份

切换用户组、调整费率或停用新收款后，已有订单、退款和付款仍使用已经封存的原账户、通道、金额和业务号核对。新策略影响后续获准行为，不能让新凭据或另一通道接管不确定的历史交易。
