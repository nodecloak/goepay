# 统计、资金明细与日终对账

运营人员用统计发现业务变化，财务和商户用原订单及流水解释金额。报表回答“发生多少”，资金明细回答“余额为什么变化”；先选口径，再把异常追到原业务。

## 从哪里进入

| 维度 | 管理员入口 | 商户入口 |
| --- | --- | --- |
| 运营概况 | 仪表盘 `/admin/dashboard` | 仪表盘 `/merchant/dashboard` |
| 每日交易 | 交易管理 → 交易统计 → 每日交易统计 `/admin/trade/stat/daily` | 交易管理 → 每日交易统计 `/merchant/trade/daily-stat` |
| 商户 / 通道 | 商户交易统计 `/admin/trade/stat/user`；通道数据统计 `/admin/trade/stat/channel` | 查询自己的订单与通道范围 |
| 地区 / 支付用户 | 地区数据统计 `/admin/trade/stat/province`；支付用户统计 `/admin/trade/stat/buyer` | 地区数据统计 `/merchant/trade/province-stat` |
| 余额、冻结与费用 | 商户管理 → 资金明细 `/admin/merchant/record` | 资金明细 `/merchant/record` |
| 对外付款 | 转账付款 → 付款账号统计 `/admin/transfer/stat`、通道数据统计 `/admin/transfer/channel-stat`、商户代付统计 `/admin/transfer/user-stat` | 在本人代付记录和资金明细核对 |
| 会员支出 | 商户管理 → 用户组购买 `/admin/merchant/group-buy` | 账户中心 → 购买会员 `/merchant/account/groupbuy` |

## 完成一次日终核对

1. 选定日期和页面使用的时间字段，固定商户、支付方式、通道和状态条件。核对页面时区，避免一份按支付时间、另一份按创建时间直接相减。
2. 查看每日统计，定位数量、金额或成功率的异常，再切换商户或通道维度缩小范围。汇总和列表必须使用相同筛选条件。
3. 打开一笔具体订单，核对订单金额、实付、实际通道、支付时间和退款。用原订单号跳到资金明细，查看收入、费用、冻结与后续变动。
4. 对当日退款、结算和转账分别按原业务号核对。申请、预占、完成、释放可能发生在不同日期，不能只用“当天收款减当天付款”解释全部余额。
5. 确认异常已有业务证据或待核对状态，再导出当前条件下的数据。核对导出范围，不把列表当前页或截图当作完整结果。

## 用哪一种金额回答问题

| 问题 | 需要核对的字段或记录 |
| --- | --- |
| 用户实际付了多少 | 原订单实付与可信支付确认 |
| 商户获得多少收入 | 原订单费用快照及关联收入 / 费用流水 |
| 为什么余额不能全额使用 | 可用与冻结明细、结算周期、保证金及原预占来源 |
| 一笔退款到底退了多少 | 原退款金额、累计已退、完成状态和账务扣减 |
| 提现到账多少 | 原结算总额、手续费、净额和机构出款结果 |
| 报表为何有未知地区 | 该记录没有可核实的地区来源，不自行归入某省 |

## 非商品收款的资金也要分开查

充值从 `/merchant/account/recharge` 发起，按原充值单的服务端确认与资金明细判断入账。会员购买影响费用支出、有效组和到期时间；保证金 `/merchant/account/deposit` 可能有持续要求、观察窗口及独立退还审批；邀请返现 `/merchant/invite` 以有效政策和已确认奖励为准。

对这几类业务按类型和原号筛选流水，再与对应申请或购买记录核对。充值成功页不代替入账，保证金退还申请不代表立刻可用，邀请人数也不能直接推算到账奖励。

## 发现差额后的处理

保留筛选条件和原业务号，沿“订单或申请 → 原执行结果 → 关联资金明细”查看。未知业务继续按原记录核对，不通过改状态或补一条随意流水让总数相等。报表没有任意改写财务事实的入口。

向运营方提供商户号、原订单 / 退款 / 结算 / 转账号、时间、错误及已核对步骤即可，隐藏完整收款账号和凭据。受限管理员及商户只能导出当前权限范围内的数据。
