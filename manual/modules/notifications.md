# 业务通知、消息提醒与打印

开发人员处理支付结果的服务端通知，商户配置自己接收的提醒和设备，管理员维护平台渠道、模板与公告。先确定消息的用途，再配置相应入口。

## 从哪里进入

| 任务 | 管理员入口 | 商户入口 |
| --- | --- | --- |
| 业务系统支付通知 | 订单管理 `/admin/trade/order` 的通知详情与重新通知 | 订单管理 `/merchant/trade/order`，接收地址由自己的业务后端提供 |
| 平台提醒服务 | 系统管理 → 系统设置 `/admin/system/settings` 的消息提醒、短信、邮箱分类 | 使用运营方已经开放的渠道 |
| 商户个人提醒 | 商户管理 → 商户消息提醒 `/admin/merchant/notice` | 账户中心 → 消息提醒设置 `/merchant/account/notice` |
| 打印服务与设备 | 系统管理 → 订单打印配置 `/admin/system/printing` | 账户中心 → 订单打印设置 `/merchant/account/printing` |
| 公告 | 系统管理 → 公告配置 `/admin/system/anounce` | 查看已发布的站内公告 |

## 先选择通知类型

| 类型 | 用来做什么 | 完成依据 |
| --- | --- | --- |
| 平台发给商户业务系统的签名通知 | 后端确认支付并交付业务 | 验签、金额和订单校验、幂等更新及有效响应 |
| 邮件、微信、短信、机器人、语音 | 提醒人查看收款、余额、投诉等事件 | 原投递任务和接收状态，不替代交易查单 |
| 小票打印 | 将允许订单发送至已配置设备 | 原打印任务结果和设备反馈 |
| 站内公告 | 向商户发布运营内容 | 正确的显示范围和发布状态 |

## 开通一条商户提醒链路

1. 管理员选择渠道，保存已开通服务的有效凭据。例如邮件需有效 SMTP 账户；微信模板需匹配应用、模板 ID、模板字段和接收身份；机器人需对应 Token 或 Webhook。
2. 在平台设置开放商户渠道与具体事件。按页面提供的事件选择能力配置，不能假定每个事件都支持所有渠道。
3. 商户本人进入消息提醒设置，绑定可信接收身份，再为需要的订单、余额、投诉、会员等事件选择可用渠道。普通联系电话不自动成为已验证短信接收人。
4. 保存对应区块并重新读取，核对接收目标、事件、金额阈值、开关及模板完整性。机器人保存凭据与完成绑定是不同步骤。
5. 在模拟环境触发已授权事件，查看原任务的排队、受理、未知和完成状态；业务事件本身也应在原订单或原申请中成立。

## 渠道字段与保存边界

| 渠道 | 必备字段与决定 |
| --- | --- |
| 邮件 | 启用的 SMTP 账户、发件身份、正确接收邮箱 |
| 微信模板 | 正确 AppID、模板 ID 和对应 OpenID；模板支持的事件需完整配置 |
| 短信 | 有效网关、该业务事件专用模板、可信手机；余额、投诉和会员到期不能覆盖登录验证码模板 |
| 群机器人 / Telegram / QQ Bot | 对应平台凭据和接收目标；需要绑定时完成绑定后读取状态 |
| 云喇叭 | 平台 `agent_id`、`agent_secret`，商户设备编号与事件配置 |
| 小票打印 | 平台 APPID、APPSECRET，商户打印机序列号、份数与订单范围 |

平台硬件、加密凭据与普通设置有各自保存边界。点击普通设置保存后，还应确认打印或云喇叭区块自己的保存结果。测试发送会联系实际服务或设备，使用前确认当前环境和收件目标。

## 没收到消息时如何定位

先查原业务是否发生，再查平台渠道与事件开关、商户个人设置、可信目标、凭据和模板，最后查看原投递任务。设备或外部发送结果未知时先核对，重复点击可能再次播报或打印。提醒失败不能据此判定支付失败。

若平台订单已支付而商户业务系统未更新，查看原通知地址、签名校验、金额核对、响应和幂等处理。修复后从原订单重新通知；这不会再次向用户扣款。其交互过程见[收款与订单中的支付时序图](./transactions.md)。

公告在公告配置中填写标题、正文、排序及颜色，预览后设置显示 / 隐藏并重新读取。公告列表、商户弹窗、注册公告和页脚属于不同内容入口，按实际展示位置分别维护。
