# 进件、风控与投诉

管理员维护进件资料和风险政策、处理投诉；商户提交自己的本地申请、补充资料并查看管控记录。先区分平台内审核与支付机构资格，再判断需要调整资料、限制交易还是从原订单退款。

## 从哪里进入

| 任务 | 管理员入口 | 商户入口 |
| --- | --- | --- |
| 进件资料渠道 | 进件管理 → 进件渠道配置 `/admin/applyments/channel` | 使用运营方开放的渠道 |
| 申请与本地审核 | 进件管理 → 进件商户管理 `/admin/applyments/merchant` | 商户进件 → 进件商户管理 `/merchant/applyments/merchant`；新增 `/merchant/applyments/create` |
| 子商户绑定 | 进件管理 → 子通道管理 `/admin/applyments/subchannel` | 支付通道 `/merchant/subchannel`，按实际开放能力查看 |
| 管控记录 | 进件管理 → 商户管控记录 `/admin/applyments/mchrisk` | 商户进件 → 商户管控记录 `/merchant/applyments/mchrisk`，本人只读 |
| 交易限制 | 交易管理 → 黑名单管理 `/admin/trade/blacklist`；其他功能 → 风控记录 `/admin/other/risk` | 查看具体拒绝提示，向运营方提供原业务号 |
| 投诉处理 | 交易投诉 → 投诉记录 `/admin/complain/list`、投诉统计 `/admin/complain/charts`、同步任务 `/admin/complain/task` | 交易投诉 `/merchant/complain` |

## 提交与审核一份本地进件资料

1. 管理员在进件渠道配置填写渠道名称、服务商和资料表单 JSON，保存并核对启用状态。此入口配置资料，不自动开通支付机构产品。
2. 商户新增进件，填写当前表单要求的经营名称、联系人、联系电话、进件渠道 ID 和备注。管理员操作时同时核对所属平台商户。
3. 保存后查看草稿，从原记录提交本地审核。当前通用资料流程中的“提交”进入本地审核中，不会自动向机构发送进件。
4. 管理员查阅原资料和历史，按允许动作标记待补充、通过或驳回，并记录意见。待补充时由商户修改原资料后再提交，审核中按页面限制处理。
5. 如确需机构入网，由运营方使用已验证、实际接入的对应适配流程另行完成。取得真实上游子商户号和产品资格后，核对绑定通道、审核及启用状态，再验证交易能力。

**本地“已通过”不是支付机构进件通过。** 当前本地资料和人工审核可独立使用；未接入的外部进件分支不能靠新增同名通道自动生效。

## 处理一次风险限制

按商户、订单、时间和类型查原风险记录，核对来源、命中目标及实际交易。风控记录含人工记录与核实事件，并非所有拒绝提示都会自动出现在同一列表。需要调整黑名单时选择页面支持的类型，填写准确目标和原因，保存后读取作用范围；解除前复查最初原因。

频率、金额、商品和人机验证等规则在系统设置的风控检测 / 支付相关维护，订单名称限制另有 `/admin/system/order-subject-policies`。先用模拟环境验证命中与未命中场景。规则改变不撤回已有支付，对受影响原订单仍应查原单。

## 从投诉到实际处理

查到原投诉后核对商户、原支付、金额、累计退款和处理历史，再记录回复或状态。需要退钱时进入[退款模块](./refunds.md)，确认原退款结果后再补充处理证据。本地“已处理 / 已关闭”和本地回复不等于机构投诉关闭或已发送上游回复。

配置同步任务时核对通道及执行间隔，并确认真实同步适配器已接入；保存计划本身不能证明同步完成。商户管控记录中的状态也需按其来源核实，不能将本地标签当作机构实时状态。

获取用户标识入口 `/admin/other/get-token` 只适用于已配置应用的授权身份流程。核对标识所属 AppID，避免将一应用 OpenID 用于另一应用支付或结算。
