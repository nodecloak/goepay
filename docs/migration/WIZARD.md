# 易支付迁移向导

管理后台「系统管理 → 易支付迁移」提供 SQL 备份上传、预检查、确认导入和结果查询。仅本人超级管理员可操作。向导导入当前 GOEPAY 实例的数据库，不能覆盖已有商户或财务数据；已在运营的实例只可预检查，不可执行导入。

## 迁移前准备

1. 准备独立、全新的 GOEPAY 安装，配置独立主密钥和初始密码。先执行 `/app/cli migrate`，再执行 `/app/cli seed-admin`，仅创建 `admin` 超级管理员，使用 `GOEPAY_SEED_PASSWORD` 登录。Compose 环境可用 `docker compose exec api /app/cli seed-admin`。**不要先执行 `seed-local`**，该体验命令会创建示例商户，使目标不再为空。`seed-admin` 不覆盖已有管理员凭据，不创建商户或财务数据。暂停目标的公开注册和业务入口，不配置或启动自动资金任务。
2. 原站停止新增支付、退款、转账和结算，等待在途业务结束。保留原站和原数据库备份，暂不修改域名。
3. 从原数据库导出一致的 UTF-8 MySQL SQL 备份。例如对 InnoDB 数据库：

   ```sh
   umask 077
   mysqldump --single-transaction --quick --skip-triggers --hex-blob --default-character-set=utf8mb4 -u backup_user -p SOURCE_DATABASE > epay-backup.sql
   ```

   密码在提示中输入，不放在命令行或截图里。混用非事务表的数据库仍须在停写状态下取得一致备份。

4. 选择原版本 `epay_pro` 或 `epay_release`。表前缀可留空自动识别；存在多个同类表族时必须明确选择，唯一的无前缀表族也可识别。文件上限为 **64 MiB**，仅支持未压缩 SQL；最多256张表、250,000行、每表512列、合计2,000,000个字段值。超限、字符集不支持或解析失败会明确拒绝，不截断数据。反向代理也须允许64 MiB文件及额外的multipart开销。

## 向导流程

上传备份后，向导显示源文件 SHA-256、表计数、可原生导入的数据、仅归档的数据、金额汇总以及阻塞项。此时不创建商户、不改变余额，也不执行原 SQL。

确认源站已经停写并保留一致备份，确认已经理解归档范围，输入 `MIGRATE` 后才可执行。导入再次核实当前会话、文件摘要和目标为空条件；预检查通过后新增的目标业务数据也会阻止导入。

执行结果与业务数据在同一事务中提交。重复点击已完成任务不会再次创建期初余额。若网络断开或结果未知，使用「读取当前状态」，不要重新上传或重复提交来猜测结果。失败会回滚该事务的商户、订单和账务；不恢复旧数据库覆盖新的业务数据。

## 数据范围

| 数据 | 处理 |
|---|---|
| 商户编号、可用余额、可验证的注册时间 | 原生导入；可用余额建立平衡的期初双边账 |
| 普通未支付/已支付订单、原商户订单号、平台订单号、名义金额和时间 | 原生历史导入；支付类型通过原类型表 ID 映射；历史已支付订单不再入账、不补发通知 |
| 有明确成功证据且金额一致的历史退款 | 进入只读历史记录，不生成可执行退款 |
| 源文件全部表、全部原始字段 | 原始备份加密保留；表计数区分原生导入与仅归档 |
| 用户组、支付通道、站点配置、旧密码/API密钥、实名资料、插件记录等未转换字段 | **仅加密归档，不自动成为 GOEPAY 的有效配置、账号或授权** |

原生导入商户保持停用，使用新生成的随机 API 密钥；不会把旧的弱密码散列当作新登录凭据，也不会自动信任原通道、实名或资金操作授权。因此，此向导不是零停机切流，也不表示所有旧插件功能已经转换。完整原始备份的保全与全部功能的原生转换是不同的结果，确认页会明确提示。

## 会阻止导入的情况

- 目标已有商户、订单、流水、资金占用、任务或其它受检查的业务数据。
- 金额精度错误、负余额、孤立记录、重复业务号、未知版本/状态或不完整数据。
- 冻结订单、预授权、非普通业务场景、未决退款/转账/结算、非零保证金，或当前模型不能可靠表达的资金义务。
- 退款状态缺失明确金额证据、实收与名义金额不同而尚无专门映射，或存在不能安全映射的合单。
- 备份包含不支持的数据修改语句、表达式或不完整的 SQL。向导不执行上传的建表、触发器、存储过程或 PHP 文件。

不要通过修改 SQL 中的余额或状态来绕过阻塞项。应在原站完成相应业务或制定明确的人工迁移方案后重新取得一致备份。

## 安全与保全

完整备份和内部迁移计划使用 GOEPAY 主密钥加密保存，并绑定任务与用途；公开任务视图不包含 SQL、密码、密钥或证件值。应用端上传只在受限内存中处理，不创建明文临时 SQL 文件。自带 Nginx 为迁移上传单独设置65 MiB请求上限并关闭请求落盘缓冲，应用端仍严格限制64 MiB文件及128 KiB额外开销。使用其它反向代理时也应核对请求大小、超时和请求缓冲策略。浏览器不使用持久存储保存备份、凭据或确认信息。

准备任务有有效期，过期后不能执行；加密归档保留用于迁移审计，**有效期不代表自动删除备份**。请妥善备份 GOEPAY 数据库与原主密钥，丢失主密钥会使加密存档无法读取。原 SQL 备份也应保存在受限的离线位置。

准备任务每个账号24小时最多20次、全局24小时最多64次，加密暂存总量上限512 MiB。达到限额时拒绝新增，不自动删除已有归档；需由管理员按数据保全要求进行离线维护。

## 核对与切流

导入后核对商户数量、订单数量、期初余额、退款历史及账务核对结果。随后重新配置 GOEPAY 的用户组、通道、站点设置和商户登录资料，逐项复核并按需要启用商户。资金操作只在本地模拟或服务商正式沙箱中验收。管理员自行完成通道开通与小额验收后，才能安排域名和商户接入切换。

原站保持只读，直到确认新系统账务、回调、查询和结算符合预期。向导不会修改原数据库、切换域名、发起支付、退款、出款或启用定时任务。
