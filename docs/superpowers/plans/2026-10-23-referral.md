# Referral Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking. 本会话沿用用户已经授权的并行 agent 分工；未提供的执行技能不得虚构调用。

**Goal:** 实现真实注册推广关系、邀请页与列表、受原订单手续费预算约束的一次性奖励，以及在普通退款前预留、失败恢复、成功撤销的完整资金闭环。

**Architecture:** 56 固定注册关系；57 固定新订单返现条款并在可信支付入账事务内发奖；58 为退款建立独占回收账户和不可变资金来源证据。奖励、退款及回收使用原订单锁协调，所有分录使用既有不可变复式账本；页面、关系资料或平台池余额均不能代替原单资金证据。

**Tech Stack:** Go、pgx/PostgreSQL、Vue 3、现有资金授权、HMAC/AEAD、既有 PostgreSQL jobs、synthetic HTTPS 通道测试。

**Spec:** [referral-evidence.md](../../design/referral-evidence.md)。该证据文档区分 Release 可读逻辑、Pro 可读路由/定时分支与加密核心。

## Global Constraints

- 项目目录为 `E:\GOEPAY`；不使用会话默认的 `D:\GOEPAY`。
- 不访问生产环境、不读取导入通道密钥、不发起真实资金交易。
- 55 已固定的全库候选单独验收；56–58 属于下一个候选，不混写旧 migration。
- 未经完整 58 回收闭环验收，不开放奖励配置，不部署“可发不可撤”的中间版本。
- 没有 Git 仓库；以限定源文件清单、SHA256、固定候选和验证日志形成检查点，不虚构提交。
- 所有金额为整数分，百分比为整数 BPS；接口金额/ID 采用字符串，不用浮点金额。
- 旧订单没有返现快照时不追补；旧推广码、不明历史关系、修改状态后的旧付款均不能变成新奖励依据。
- 普通支付、充值和会员购买必须有明确业务来源。不得按商品名称或商户订单号猜测充值。
- 关系、政策版本、条款、已发奖励与账本不可改写；失败重试产生新的业务意图并保留旧证据。
- 先完成原单/业务行锁，再一次升序锁齐本事务会使用的全部账户，然后写分录；不能在持有账户后再锁推广人商户行。
- 每个阶段需要实际红绿证据、独立审查；最终同一固定源分别跑 Windows 全库和 Linux race/vet。

## 已知边界与明确开放能力

可先开放 `immediate + platform_fee + any_successful_refund_voids_reward`：奖励来自原单平台手续费，任何成功的部分/全额普通退款都撤销整笔仍有效的奖励。后一个策略是本项目明确的新保守策略，不能写成已经证实的 Pro 兼容行为。

Release 有订单金额/手续费/利润三种基数及不同封顶规则；Pro 可读日结是昨日 `SUM(realmoney)`，与即时计算并不相同；Pro 即时、会员及退款回收核心加密。第一版显式拒绝 daily、profit、groupbuy reward 配置。利润基数缺少经审计的渠道成本快照，不能伪造利润。

现有 `PurchaseMembership` 把 price 从商户余额转入 clearing，没有独立会员收入/奖励预算或会员退款生命周期。会员购买继续工作，但不得借普通支付 fees 支付会员推广奖励。它需要独立收入预算与购买事件绑定的后续设计。

冻结/解冻订单收入不重新发奖，不触发奖励撤销。渠道分账 PS/PR/PF 与买家普通退款不同：PR 回收给原商户不会自行撤销推广奖励。

### 资金定义

| 符号 | 定义 |
|---|---|
| F | 原订单不可变 `platform_fee` |
| R | 原订单仍有效、尚未永久撤销的奖励，取已验证 award.amount |
| S | 新退款插入前，其他非 failed 退款已占用的原单 fee_amount 合计 |
| G | 本次按现有规则固定的退款 fee_amount |
| U | 原手续费尚可直接用于本次退款的预算 `F - R - S` |
| K | 需从本次追回奖励补给手续费池的金额 `max(0, G-U)` |

要求 `0≤R≤F`、`0≤S≤F-R`、`0≤G≤F-S`、`0≤K≤min(R,G)`。非法原单证据不能被 `max(0,...)` 悄悄修平。

“任意成功退款撤销整奖”下，如果 R 仍有效，前面不存在成功普通退款；存在则表示已丢失回收记录，必须报来源异常。前面有 pending/unknown 回收时，新退款必须冲突；同退款号重放读取原快照。前面仅 failed 回收时必须有完整 R 恢复证据。

奖励已经被成功撤销后 R=0，未来退款使用原手续费剩余预算 F−S，不再从推广人扣第二次。

**注意 S 的历史口径：** 计算发生在本次 refund INSERT 之前，不能把本次 G 再计入 S。持久化 S 及前驱证据，历史 invariant 不能在未来退款增加/失败后把“当前其他退款总和”当成过去的 S 重算。

### 分录与状态

新增账户 kind `referral_clawback_reserve`，owner=0、scope_id=refundID。账户身份、归属、refund/source 绑定不可变。

| 时点 | 必须同事务的分录 |
|---|---|
| 新 refund 预留 | 推广人 available→escrow R；若 K>0，escrow→fees K；旧逻辑 fees→fee_reserved G；旧逻辑商户本金预留继续执行 |
| pending / unknown | 保留 escrow R−K 及 fee_reserved G；不释放、不二次追回、不换退款号偷偷重发 |
| failed | 旧逻辑 fee_reserved→fees G；若 K>0，fees→escrow K；escrow→推广人 available R；旧本金返还继续执行 |
| succeeded | 旧逻辑 fee_reserved→clearing G；escrow→fees R−K；旧本金结算继续执行；奖励永久 voided |

零金额不创建虚假 journal；各 journal key 固定：

```text
referral-clawback:<refundID>:reserve
referral-clawback:<refundID>:fee-contribution
referral-clawback:<refundID>:restore-contribution
referral-clawback:<refundID>:restore-reward
referral-clawback:<refundID>:release-remainder
```

原有 `refund:<id>:reserve|resolve`、`refund-fee:<id>:reserve|resolve` 保持语义。不能通过第二条同名 key 静默吞掉原金额不一致；每次依赖幂等前先验证不可变原意图和分录形状。

新增 `referral_refund_clawbacks` 至少保存 refundID unique、rewardID、order/merchant/promoter、F/R/S/G/K、escrow account、原 reward hash、request hash、各 journal 引用、state、result hash、created/resolved 时间。`reward_id` 的非 failed 部分唯一索引包括 succeeded：成功后永久防止第二次扣奖，pending/unknown 阻止并发回收，failed 有恢复证据后可新退款意图。

原请求 HMAC 覆盖退款原号/金额/merchant与fee分配、原 award/terms hash、F/R/S/G/K、账户 ID、refund policy。结果 HMAC 覆盖原请求、最终状态、原 provider operation 身份及所有结果 journal 引用。SQL 检查形状，Go 读时还必须复验 keyed proof，不能以“32 bytes 非空”当可信结果。

### 已找到的锁顺序反例与修复范围

`postByAccountIDs` 仅保证一对账户顺序；连续调用会保留早先锁，不能推出整个事务有序。

反例 A：支付事务已有 fees 锁、发奖等待 promoter.available；退款事务已经追回奖励、持有 promoter.available，再向 fees 补 K，双方等待。仅给 clawback helper 自己排序不足。

反例 B：新退款先预锁 fees，再等待 merchant.reserved；现有 transfer resolver 先转本金 reserved→clearing，持 reserved 后才认费 reserved→fees，形成另一环。

已确认分工：

- returns agent：`ReserveRefund`、`resolveRefundTx`，包括没有奖励的旧退款路径；`resolveTransferTx` 成功的 reserved/clearing/fees 多分录，以及失败返还账户。首个 post 前调用 root 的 `lockLedgerAccountSet`。
- root：`markPaid`、`settlement_payout_resolution.go` 以及检索到的 bank/return 多分录路径；每个事务提前枚举整个账户集合。原有只涉及同一对账户的 sharing 观察分录不随意扩锁。
- 新专属 scope 账户在旧账户全预锁后创建时，只锁它自己，不再申请其他旧账户，避免逆序。
- 不新增“账户→promoter merchant”锁。原单债权来自条款，不用当前商户启用状态重写已发奖励。
- 不通过所有退款一律额外锁 clearing 的方式掩盖反例；这种共同前缀会额外序列化本不访问 clearing 的预留事务。

## U/K 核对表

| F/R/S/G | K | unknown 时 fees 可用原单预算 / escrow / fee_reserved | failed 后原 fees / 推广人奖励 | success 后原 fees / 推广人奖励 |
|---|---:|---|---|---|
| 10/5/0/0 | 0 | 5 / 5 / 0 | 5 / 5 | 10 / 0 |
| 10/5/0/3 | 0 | 2 / 5 / 3 | 5 / 5 | 7 / 0 |
| 10/5/0/8 | 3 | 0 / 2 / 8 | 5 / 5 | 2 / 0 |
| 10/5/0/10 | 5 | 0 / 0 / 10 | 5 / 5 | 0 / 0 |
| 10/0/5/5 | 0 | 0 / 0 / 5 | 5 / 0 | 0 / 0 |

表中“推广人奖励”表示本奖励尚未被扣回的合同金额，不是对整个推广人钱包余额的声明。奖励回收前可能已经花掉，实际 reserve 必须检查其 available 足额。

预算守恒：unknown 时 `(F-R-S+K-G)+(R-K)+G = F-S`；failed 恢复到 fees `F-R-S` 且推广人恢复 R；success 为 fees `F-S-G`、奖励撤销。这些等式只能在原来源证据都可信、K 来自独占 escrow 时使用，不能用池余额代替来源。

## 实施时增加的结果凭据与锁约束（59）

独立复核发现，`provider_operations.state` 是发送操作缓存，不能在重放时当作本次可信退款结果。未知退款的同号重放保持只读；只有实际适配器验签后的原号补查才能形成新的 provider 结果。真实补查还必须能修复不可信缓存的旧终态，不能被旧 terminal guard 永久卡住。

因此新增 migration59，保留旧 migration5 的已部署 checksum。退款出生时固定 `result_evidence_version`：迁移存量为1，新生必须为2且不可降版。新退款终态必须有同事务的 provider 或 internal 结果证据、原非终态→终态审计、原本金及手续费结算分录和 HMAC。内部 `Store.ResolveRefund` 也要形成明确的 internal proof；已经终态但缺 proof 的记录不能通过重新调用服务补封为可信。checker 分别检查结果父表、缺 projection 和分100条读取的 HMAC。

除了全部实际分录账户一次按 ID 预锁，还要把稍后 INSERT 或 audit 触发器必拿的 merchant FK `KEY SHARE` 提前到任何账户锁之前。已实测四个反例：支付奖励、退款回收出生、退款结果、转账结果。如果先占钱包后等待 merchant FK，会与既有会员/保证金的 merchant→wallet 顺序相反。提前的锁不检查当前 enabled，也不使用 `FOR UPDATE` 或 `FOR SHARE` 重锁，旧单权利仍由原快照决定。
