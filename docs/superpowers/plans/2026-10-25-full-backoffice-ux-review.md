# 双后台全页面UX复核与修复计划

**用户范围澄清：订单只是举例，管理后台和商户后台全部页面都必须review。** 本计划扩展订单动作计划，不以订单一页的通过代替其它页面验收。

**Goal:** 从原Pro两个入口的真实菜单→视图组件→编译模块逐一建立来源，再核对当前页面按钮、状态分支、确认、字段、筛选、权限及错误/空态，修复确认差异。

**Architecture:** 自动生成可复核来源清单，人工判定实际差异；逐动作记录当前入口和后端支持。通用CRUD、静态菜单、字段词典和mock通过均不能算行为相同。保留当前资金模型与审计，确需差异时在对应操作中明确，不用无效按钮冒充实现。

**Tech Stack:** 本地Pro静态JS/菜单、Vue3、Go、PostgreSQL、Vitest、Playwright。

## 顺序与交付

- [x] 全82个原菜单叶节点绑定原组件和实际JS SHA，提取原操作候选、字段、状态文本和接口；82项全部绑定。
- [x] 核对全部当前路由的真实组件和静态能力入口；已完成的六类字段映射只作为这六类证据，未据此推断其它页面完成。
- [x] 在本地模拟后台逐页读取82页真实DOM，记录按钮、表头、表单与截图；0页面/HTTP错误，0外部或业务写请求。仅代表观察基线，越权和各状态分支仍按后续动作测试。
- [ ] 建立每页差异：原UI存在/当前入口位置/服务端行为/状态条件/修复文件/对应实际测试。禁止以全仓库关键词命中代替本页支持。
- [ ] 优先完成订单动作闭环，同时复查商户、用户组、通道/支付设置、分账、结算、代付、报表、账户与系统设置等全部动作族；其它业务插件仅按原用户指定暂缓，不扩展暂缓范围。
- [ ] 每项可确认修复先回归测试再实现；共用组件变化需覆盖两个后台及手机/桌面。对原加密控制器无法确定的业务规则保留明确边界。
- [ ] 最终报告分别列出已对齐、实际缺口、原材料不能确认、用户明确暂缓，不能统一写成partial就称完成；不在每页或每类完成时结束本任务。
