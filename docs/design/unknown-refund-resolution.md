# 无法自动核对的“未知”退款

## 背景

退款请求发出后，如果支付机构的应答丢失、超时或无法确认，退款记为 `unknown`，资金保持预留，由 Worker 的 `refund.reconcile` 任务调用通道的退款查询来确定终态。

- 55 个插件通道实现了退款，但只有 2 个实现了退款查询。其余通道上的未知退款无法被自动核对。
- 插件把机构返回的非成功状态统一包装为 `rejected(...)`，而 `definiteProviderRejection` 只认可微信/支付宝的少数错误码，因此插件通道上被机构明确拒绝的退款也记为 `unknown`。
- 改动前，后台没有处理未知退款的入口（`Store.ResolveRefund` 只被测试调用），而数据库要求已发送给机构的退款只能凭经认证的机构证据进入终态（迁移 000059 的不变量）。

结果是：这些通道上的未知退款会长期冻结商户资金，运营无法在系统内结案。下文“已实现”一节给出了现在的处理方式。

现在 `cli check-channels` 会为每个通道输出 `unknown_refund_reconciliation`（`automatic` 或 `manual`），API 以 configured 模式启动时也会对 `manual` 通道记录告警，便于上线前评估。

## 可选方案

1. **为主要插件补充退款查询**（推荐优先做）。按各机构文档实现 `QueryRefund`，未知退款即可沿用现有证据模型自动核对。需要逐个通道对照机构接口实现并联调。
2. **按通道维护“确定失败”的拒绝码表**。只把机构文档明确表示“未受理、未退款”的错误码视为确定失败，其余仍为未知。需要逐个插件核对状态码含义；分类错误可能导致重复退款，必须有对应测试。
3. **运营核实结案**（兜底）。超级管理员在机构后台核实后，经资金密码授权，把一笔未知退款标记为成功或失败，必须填写机构侧单号与说明，写入不可变审计。需要新增“运营核实”证据来源并扩展 000059 的不变量（只新增迁移，不改已部署迁移），属于资金证据模型变更，需单独评审。

建议：方案 1 覆盖主要通道，方案 3 作为无法查询时的兜底。方案 2 仅在机构文档足够明确时逐个启用。

## 已实现：运营核实结案（方案 3）

- 迁移 `000197` 新增不可变表 `refund_operator_attestations`，并在结果证据中加入 `operator` 来源：它必须关联原发送操作，且同一事务内存在对应的核实记录；证据的出生守卫与 `provider_refund_result_invariants` 视图都检查这一点，`cli reconcile` 也会逐条复核其 HMAC 证明。
- 接口：`GET /console/v1/admin/refunds/{id}/attestation` 返回是否可核实及原因；`POST /console/v1/admin/refunds/{id}/attest-result`（`state`、`provider_reference`、`note`）为强制资金授权操作，只允许超级管理员本人会话。字段与状态码见 `api/console.openapi.json`（由 `docs/tools/refund-attestation-openapi.mjs` 生成）。
- 只处理没有自动路径的退款：已发送且操作状态为 `pending`/`unknown`、原通道不支持退款查询；或从未发送的预留（只能核实为失败，证据来源为 `internal`）。发送中、已终态、合单退款和支持查询的通道一律拒绝。
- 记账与机构结论完全相同：成功转入清算，失败退回商户可用余额，同时更新原发送操作的状态并写入后台审计。
- 退款查询（`/api/pay/refundquery`）对已结案的退款直接返回保存的终态；对无法查询的通道返回保存的处理中状态，而不再报“查询不可用”。

方案 1、2 仍可按通道逐步推进，以减少需要人工核实的退款。

## 并发与结果未知时的恢复

- 未填写 `out_refund_no` 的 API 请求，在原订单锁内选择当前或前一个十分钟窗口的退款号，并在同一事务内预留退款；跨窗口的并发重试必须先等待原预留提交。需要连续发起金额相同的独立部分退款时，应明确填写不同的 `out_refund_no`。
- 人工核实在现有事务内恢复并验证原支付账户，不再额外申请连接；无法验证账户时不开放核实资格。
- 提交应答丢失后，页面保持禁写。只有成功读回同一退款的新状态后才能解除锁定；若仍可核实，管理员必须重新勾选确认。读取等待、读取失败或返回其他退款均不能恢复提交。
