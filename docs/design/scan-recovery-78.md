# 付款码查询与超时撤销78

本地依据：`reference/server-pro/plugins/payment/wxpay/WxpayPlugin.php:373–428`与`alipay/AlipayPlugin.php:662–738`。原付款码在USERPAYING/SYSTEMERROR或10003/20000时按原订单查询，最多六次、每次约三秒；确认成功才完成入账，仍在支付中则尝试原号撤销。本轮起始Go只有一次扫码发送及只读异步查询，缺少原超时撤销，不能以普通close替代。

本轮只用临时密钥、本地TLS及隔离PG测试，不访问生产或真实支付接口。1..77 SQL已固定，后续来源若需DDL只新增78。固定91独立验证77，不修改其源码。

公开主依据：[微信付款码撤销](https://pay.wechatpay.cn/doc/v2/merchant/4011937361)要求先查询、建议付款至少15秒后撤销，限七天以内、双向证书；撤销可能关闭未付交易，也可能退回已付交易。因此它是独立金融动作。[支付宝撤销接口](https://aipay.alipay.com/docs/subscribe/api-list/other-basic-interfaces/trade-cancel.html)区分close/refund，retry_flag不能当作已经撤销。

实施按以下边界推进，全部接好前不开放新外呼路径：

1. 独立`ScanCancellationProvider`适配器，仅原scan产品。微信使用原out_trade_no及APIv2签名、双向已验证TLS；支付宝使用原out_trade_no、RSA2节点验签及已验证TLS，校验回显、action/retry_flag。结果附不可由普通结构体/JSON伪造的私有认证来源，绑定原账户/产品/订单/金额与应答摘要。裸错误、错误身份、签名、退款/重试歧义不生成最终取消证明。构造和本地校验零IO，不隐含重试。
2. 持久原扫码恢复来源绑定原attempt/商户/通道/付款码HMAC/账户/金额与等待期限。只读轮询不再次发送付款码。首次撤销前原事务提交独立单次claim、审计和收款屏障，最终锁后再次检查原订单仍未入账、当前账户不变和最小等待/有效期。若已被合法回调入账，放弃新撤销，不把已付订单走普通close。
3. 屏障存在时，回调/主动及后台查询不得越过未决撤销直接入账。确定原撤销或可信终态关闭原pending订单；未知保持原号查询与明确未决状态，不能把随后SUCCESS当作撤销一定没有执行。不得借新授权、换账户或重发原付款码解除屏障。原资金、退款和奖励来源不得被外发操作回滚或重复入账。
4. 原API保持签名与字段；成功查询沿用原scan响应。等待、查询和撤销分别有界且可取消，不占用数据库事务等待网络。不同恢复消费者、重复API/回调、超时、崩溃、撤权、换付款账户、午夜和DB损坏都需要测试。普通非scan支付、历史已付/未知来源不自动采用新规则。
5. 最后接原后台状态/明确人工核对、worker和默认关闭的独立执行开关，补CLI来源检查、实际PHP契约、双后台回归、完整候选两平台PG/race及本地无重置部署/恢复。只有适配器测试通过不能声称原scan恢复已完整实现。

原插件忽略撤销错误的行为不照搬为最终成功；Go保留可审计的未知结果。官方recall/retry_flag若提示重试，不自动复用首次发送权；后续是否需要独立有界同原号撤销重试，必须以明确来源和状态机实现，不能等同重新扣款。

## 数据库来源与后续状态机约束

主区已新增78原来源迁移及原事务创建API；后续已接入SubmitScan/独立worker流程，完整候选仍待验收。provider_attempt_accounts追加V0/V1来源锚，V0保留原MAC；V1独立MAC绑定原scopeHMAC、attempt和来源proof。来源固定原请求身份、原订单维度、15秒/3秒/6次/120秒与数据库时间/xid，恰好一条对应审计。真实77升级、无回填、并发首次权及来源写失败回滚已有专项测试；取消claim、观察链与入账屏障已按下文约束实现并专项验证；运行流程在后续阶段接入，见末尾当前状态。

不能只给原attempt追加一个可删的“需要撤销”子表，再在缺表/缺行时当成旧订单。新自动恢复若在首次scan前启用，应在原创建事务绑定原attempt身份与账户来源；既有`provider_attempt_accounts.account_hash`需使用独立版本的MAC，将账户scope、原attempt和恢复来源一起绑定。旧V0保持原MAC；V1被删来源或降成V0后，实际provider账户检查必须失败，而非恢复成可直接入账的普通扫码单。源码中的`checkProviderAccountScope`、`beginProviderAttempt`与所有真实查询/回调路径必须一起核实，不能只改一个HTTP入口。

最低等待、有效期、最多六次查询、原请求身份HMAC、当前merchant有效性及相同付款账户都由持久来源限定。普通网络未知与原指定已认证业务待支付错误要区分；不能把任意错误文本解析为原自动撤销授权。SDK适配器若要提供待支付原因，也需私有认证来源绑定原请求；数据库出错时保留原查询能力，不新造取消权限。

轮询不在数据库事务中等待网络。第一次cancel必须在锁住原订单后确认仍未入账，并同事务写入永久claim、收款屏障和审计；之后才外呼。所有`markPaid`路径在相同订单锁内重查屏障：先入账则后来的新cancel拒绝，先claim则迟到查询或回调不能入账。新cancel的未知只保留原号查询/核对，不重发付款码；可信关闭/退款终态才能结束取消屏障，成功查询本身不能证明未决取消没有执行。

未来CLI应分别检查来源完整性和已经外发但未决的取消，不能把合法排队轮询算作财务异常。所有旧历史形状测试在原兼容断言完成之后才应用78供最新检查器使用；77及以前SQL不得修改。升级前旧scan未知单不补恢复来源、不自动撤销，旧普通查询和回调继续遵循原账户与身份。

## 有界查询记录实施约束

原待支付登记已在主区实现：必须消费私有验签凭据并匹配仍在内存中的完整扫码请求，再以原身份HMAC验证应用/付款码。数据库只保存账户与请求摘要的有钥派生值、已认证错误码和应答摘要。登记、唯一审计、唯一payment.scan-recover任务同事务提交；删除任一来源不能通过重复登记补造。该阶段尚未接入口；后续接入情况见末尾。

只读ObserveScan已在两适配器实现，仍只请求原query端点。实际TLS、签名、原账户与订单号验证后生成私有来源；普通Query、修改后的结果或JSON反序列化没有此来源。回执绑定金额、币种、状态、原机构单号和查询请求/已认证结果投影的摘要。原SUCCESS、待支付、已关闭各状态有明确白名单。

接下来的查询状态采用最多12个不可变事件（六次query claim与各自observed/error），一个带MAC的原eligibility进度头。事件绑定原任务、租约摘要、原号、序号、前一事件proof、数据库时间/xid及唯一审计。首查及相邻查询至少三秒；崩溃留下未完成claim不得直接视为六次待支付，普通只读对账仍可查询。每次claim先提交，再执行网络读；迟到响应保存必须核对原claim与租约。只有六次连续认证待支付应答、原15秒/120秒窗口及仍有效的原账户/商户，才可进一步申请独立取消claim。取消入账屏障已在后续阶段实现，执行入口尚未完成；查询凭据或排队任务本身不授予撤销权。

主区现已实现上述查询链及独立取消claim/结果。取消claim绑定最终查询头、原账户来源、任务/租约和原业务号；只有最后一份待支付应答后的一个三秒间隔内可提交首次取消，并在审计等待后再次检查窗口、商户与租约。永久claim提交才有一次发送机会；网络不占用数据库订单锁。未知不得重开，确定ACK必须匹配原请求摘要，不能用应答回显机构号替代原请求上下文。保存原ACK采用永久原claim凭据，不要求仍有效的可续租worker租约，避免已经发生的原操作应答因租约过期丢失。

markPaid在原订单锁后、任何receipt/流水/奖励/打印前无条件核实来源与取消屏障，不依赖新执行开关；普通close在同一锁内也检查屏障，首次取消拒绝任何已存在的普通close操作。先入账则不取消；先永久取消claim则迟到SUCCESS不入账；只有私有验签且匹配原请求的确定取消应答关闭原pending订单，不生成退款资金流水或余额收入。原微信ACK只能证明close_or_refund，不捏造具体退款金额。删除claim、头、审计或降级账户不能恢复为普通可入账订单。CLI检查已实现并通过阶段专项；后续已接独立执行开关及worker/HTTP，默认关闭，当前实际部署91不包含78。

## 当前运行接入与验收约束

主区SubmitScan在启用新政策时先校验原通道具备只读观测和撤销能力，再于原首次发送事务创建V1来源。只有私有认证的原待支付错误才登记唯一恢复任务；历史V0重复请求仍核对原身份与账户，不补来源或再次发送付款码。原USERPAYING/10003首查等待5秒，SYSTEMERROR/20000首查3秒，其后间隔3秒、最多6次；只有USERPAYING/WAIT_BUYER_PAY继续，NOTPAY及其它终态结束本次链路。

ExecuteScanRecovery每次只领取一次原查询并先提交claim。成功观测沿用原入账路径；第六次仍在支付才领取原永久撤销权。首次已领或未完成的查询/撤销不因进程重启重新发送。撤销的已发生原应答使用独立5秒保存窗口，即使调用方取消也保留原最终或未知结果。网络读/写分别10秒有界，不持有数据库事务等待网络。

API及worker的GOEPAY_ENABLE_SCAN_RECOVERY默认false。configured模式同时要求明确的provider writes/queries、加密配置文件与商户通道映射；原只读reconciler始终不继承撤销能力。worker只按原attempt来源领取payment.scan-recover；HTTP有界等待只竞争原任务，已有worker租约时不抢占。扫码HTTP包括首次提交在内23秒有界，保留30秒写超时内的应答保存余量；未决返回原trade_no用于后续核对，V1/V2成功字段不变。

双后台订单详情只读取经核验来源和查询/撤销历史，省略旧V0状态，不暴露付款码、内部摘要或任何发送权。cancel_pending明确待核实，cancelled不表示商户余额增加；不提供重发或再次撤销按钮。CLI新增invalid_scan_recovery_sources和unknown_scan_cancellations，当前完整检查共24项；合法排队查询不算未知金融动作。新增表6张，未来完整schema78含元数据共188张。完整双平台固定源码、PHP、前端及无重置部署/备份恢复仍是发布前必需步骤。
