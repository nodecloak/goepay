# 预授权剩余冻结解除75实施计划

2026-10-24。74已冻结于候选86，双平台全库运行，主工作区开始下一项。1..73已部署不可改；冻结86中的74也保持原样。其它业务插件仍暂缓，仅本地合成PG/TLS及模拟部署，不读取真实密钥、不访问生产、不发真实资金。

## 本地原实现证据

`epay_pro/app/lib/Payment.php::alipayPreAuthPay`先查原out_order_no/out_request_no，AUTHORIZED且rest_amount>0时对该rest_amount执行一次PREAUTH_PAY/COMPLETE；FINISH时查询原交易。`alipayUnfreeze`对原auth_no的当前rest_amount解冻；每次随机新号的原实现不能直接照搬未知重发。已知代码没有自定义任意部分金额或多次capture接口。现有Go手动/自动单次COMPLETE已经实现；不能将授权累计消耗额当成原订单的已验证收款。

新增明确的“解除剩余冻结”用例，复用原UA、发送屏障、原号查询及资金保护。普通全额未消费解除继续原契约。存在原订单部分支付而未完成可信收款核对时保持待核对；不把小额交易伪装成全额支付。

## 实现顺序和不变量

1. 先写纯条款与真实PG RED。新增75迁移；旧release父记录原amount保持原授权总额，新原始金额/有效解除额分别展示。父记录新增来源头ID/修订/HMAC，0仅指原全额路径；非0必须有完整独立剩余额来源，禁止删除、清空或降级。
2. 来源绑定原order/merchant/provider attempt/channel/AppID/付款账户摘要、auth_no/buyer、原总额、68真实观察ID及source/result proof、明确剩余额、原UA、原会话/actor/版本、期限、事务和审计。观察来自签名原FREEZE查询，SUCCESS/AUTHORIZED、金额/身份完全匹配，剩额明确且0<remaining<=original；调用方金额只作CAS核对。
3. 原order→authorization→release锁序。新来源可以接管尚未发送的旧全额checking/reversal_pending意图，保留父amount、原UA及旧证据。原全额发送函数对非0来源拒绝取得发送权，避免旧并发调用在新条款上发送全额。
4. 发送前来源历史追加不可变版本，CAS原来源头，单次最多100修订。仅sent=false且未终结时允许新观察/新独立确认更新条款；旧来源不能刷新金额或延长权限。历史链缺失、父头缺失、错误actor或HMAC都阻断。sent=true后不改来源、不改UA/金额、不再发送。
5. 显式新HTTP动作携带expected_observation_id、expected_remaining_cents及expected_source_revision；管理员本人super、CSRF、独立逐动作资金确认，不能复用旧全额解除授权。观察与确认绑定当前会话；历史已发送来源的只读核对不因旧会话撤销而失效。商户入口按已有身份能力明确约束，不能用管理员证明代替商户身份。
6. 意图与来源、审计和原号恢复任务在首个外部请求前提交。先查询原支付：真实全额成功走已有PaidReceipt并使解除失败；捕获processing/unknown时只有已验签TRADE_CLOSED才有资格首次解冻。未找到交易不能消除在途扣款。原交易有不完整部分收款证据时停止并要求核对。
7. 新鲜原FREEZE查询必须再次证明同一原总额、原身份及本来源明确剩余额。最后数据库锁/审计等待后复核来源头、当前权限/期限/业务参数才竞争首次发送权；发送屏障提交后停权不能重新开放。上游只收到绑定的剩余额。
8. 解冻同步响应不直接成功。查询同一原UA，UNFREEZE/SUCCESS、精确金额/授权号/请求号及明确rest_amount=0后才确认；缺失/错额/错UA/坏签名/NOT_FOUND/HTTP错误维持未知。资金解除不生成商户入账、退款或返还账务。
9. 原读接口返回旧全额形状不变（新增字段对旧来源省略）；新来源显示原总额、有效解除额、来源修订。旧全额POST不发送新来源，原query可以按同一UA只读恢复。状态明确区分“意图已保存”“已发送待核实”“已确认”。
10. Checker从父头、来源历史、原恢复任务及审计检查，不能依赖INNER JOIN隐藏丢失。旧数据保持来源0无回填；真实74→75正记录升级保持旧列hash/原UA/原金额与原查询行为。
