# 自动结算出款的下一步边界

2026-10-24，依据本地 Settle.php、Transfer.php 及现有40/43/44/45/60资金核心复核。当前计划仍仅产生待审核原申请，不能自动付款。本文件是后续实现约束，不是能力已完成声明。

新增有限自动付款授权必须引用一个确定的计划定义版本与原生成授权，固定已主动加入的商户及受款配置版本、有效期、每项/每天/run金额与次数。不能让生成授权、原管理员一次grant或恢复任务授予付款权限。每个自动付款成员必须是该原run已经产生的原request，不能扫描当天任意待处理申请。

通道范围同时绑定明确产品、ApplicationIdentity、真实TransferAccountIdentity。现有 TransferAccountScope 为兼容人工/测试允许较弱回退，自动付款必须独立拒绝provider-only、application-only以及支付宝缺SellerID时的AppID回退。密钥轮换不应伪造新物理账户；物理账户改变必须让旧授权失效。

原毛额G=净额N+平台结算手续费F，付款仅用原申请专属reserve，不能再次扣钱包。自动模式还必须明确上游服务费的授权上限及可执行依据。银行当前只在结果/查询给出BankFeeKnown或估计order_fee，没有发送前受支付机构执行的费用上限或可信报价，不能把未知费用当0。银行自动发送在补齐能力前保持不可用，人工银行完整生命周期继续保留。钱包同样必须有具体产品与可验证费用约束，不能仅凭provider名字假设免费。

实现需抽取现有审批、prepare和claim的私有事务primitive，人工入口继续检查原grant，系统入口只接受同事务构造的有限计划proof。审计actor使用system，不能伪装原authorizer为在线管理员。授权撤销/到期阻止未claim；claim后未知只能查原TF，不能重新授权再次发送。恢复不得删除claim或更换外部号。

验收必须覆盖：生成授权不能发送；固定商户/原申请/物理账户/产品/费用上限；锁等待后的撤销与到期；并发只发一次；审计及DB失败0外呼；真实本地TLS的accepted、unknown及原号查询；原净额/费用恒等；现有分账、冻结退款及奖励资金不被借用；SQL缺父记录与HMAC损坏均可被checker发现。严格阈值Transfer族在此能力完成后单独实现，不能套普通Settle费用公式。
