# Pro余额阈值转账74实施计划

2026-10-24，主工作源码继续开发；固定85包含截至73的功能，验证过程不修改该快照。此文不是阈值功能已经可用的声明。

## 已确认原规则

可读证据为`epay_pro/app/cron/Transfer.php`：`auto_settle_money`必须非零，`transfer_alipay`为全局明确通道；启用商户、开启结算、支付宝收款、余额**严格大于**阈值，UID倒序最多5个。先选择5个，再跳过明确关闭结算的组，不从后续商户补足。费率取组的非空覆盖，否则全局；整余额作毛额，比例费half-up到分并仅受全局fee_max限制，不使用Settle的fee_min、最低结算额、最大结算额或余额留存。

原代码先外部发送再插入记录、扣余额，有发送成功但记录失败风险。Go按用户要求提升安全性：原意图、专属资金预留、有限授权、claim和审计始终在首次I/O前提交。沿用73原号查询、未知不重发；不仿照原实现的资金竞态。

## 明确实现方向

1. 现有生成计划增加明确`balance_threshold`业务模式；普通`generate_only`含义不变。阈值从对应原配置读取，0/缺失默认关闭；通道固定原`transfer_alipay`及强付款账户、具体支付宝产品。生成授权与73独立自动付款授权仍分别签发，不能把生成权限扩大为付款权限。
2. 新模式允许有界分钟/秒调度；定义版本、配置、组费率、商户主动加入、收款及通道都固定到原授权。修改配置需要重新核对和授权，不静默扩张权限。
3. 用新迁移扩展模式并添加原run的不可变阈值选择证据。按商户ID升序锁住完整授权范围和资金账户，再按UID倒序选择原前5个，保存选择时点、金额和HMAC。锁等待后重新核对期限、业务日、配置和余额；不在遍历过程中动态用新余额替换原选择。
4. 单次run中的选择及生成在同一事务内。完整范围仅进入选择快照；只为原已选至多5人记录结果，原run按该原集合结束，空选择也可完成。只为合法已选商户创建原SP及专属reserve，任何持久化异常回滚整个run。
5. 整余额超过有限授权剩余额度时跳过，**不截成部分付款**。Go不能提前消费未成熟或被冻结收入；整余额尚未全部可结算时受阻，仍不改为部分金额。报价复用现有整数手续费计算，只构造本业务允许的rate+fee_max，不复制浮点公式或错误继承fee_min/留存。
6. 同商户一天只能生成一次的旧Settle意图保持原约束；阈值分支使用独立的原run/原item意图记录，允许一天多次新增余额后的新run。不能删除旧唯一约束来放宽已有业务。`ledger_requests.settlement_plan_item_id`原父锚继续区分计划申请，缺失新子证据必须阻断，不降级为普通申请。
7. 原请求创建、读取、prepare、claim、查询、资金确认及checker按原定义模式选择对应证据。新模式的费用快照由不可伪造的私有事务上下文传入共享资金primitive，并绑定原run/item及原quote；客户端不能指定系统费率或绕过政策。原1..73迁移和旧proof格式冻结，新增加法字段必须对旧空值省略并用实际历史证明测试保持旧hash。
8. 73自动付款执行器仍只发送原当前业务日申请；绑定原有限授权与原TF，全部未知结果交由已有只读恢复任务。原Pro错误关闭通道/管理员通知另核对可信错误分类，不以网络超时当作已失败或释放资金。
9. 后台显示原“商户余额自动转账”的阈值与全局支付宝通道字段，明确整余额、最多5个及独立授权。配置和模式变更走CAS/原资金确认，UI状态切换清除旧确认；不得以页面保存成功表示执行器运行或上游成功。

### 选择证据的父锚及共享primitive

阈值选择不是可丢弃缓存。新迁移应为原`settlement_plan_runs`增加独立选择版本/哈希：0仅表示尚未开始，原选择与审计首次提交时同事务升为1；1不可擦除或降为0。重试发现父锚1但选择子证据缺失时必须停止，不能按新余额重新选择5人。旧generate_only记录维持0、不回填。原run proof格式保持，阈值选择使用独立HMAC域，绑定原run证明、完整有序资金快照、原选中集合和选择时点；读取避免递归调用readRun。

选择阶段按商户升序取得完整锁，计算原UID倒序前5名，再按原顺序生成；未选成员只保留在完整资金快照，不制造多余item。关闭组计入原选择5名后跳过，不从第6名补足。quote不会把整余额截小以适应授权额度。

### 跨run额度与批次顺序

选择证据增加事务内单调序号，父run同时锚定原序号及HMAC。不能用run ID推断生成顺序：旧的pending run可能比新run更晚执行。在原plan锁内按同业务日最大选择序号读取上一份已验证证据，固定前序run/序号/hash、原累计毛额/笔数、本次全部预定结果及新的累计值。重新授权降低限额不改写历史累计值，也不允许继续超额。

每次生成先用父子连接检查整个plan/day的证据完整性，再读取最新HMAC累计值；不能只对可丢失子表SUM而重置额度，也不逐批递归回读一天所有完整资金快照。原前序父hash、序号、业务日及plan必须一致。签名内原报价与最终items逐字段核对，实际申请ID只允许在created项中补入；0项批次也写不可逆的原选择及累计值，重试不得按新余额再次选择。计划第一次签发授权后锁定业务mode，避免混合旧业务累计来源。

现有`commitSettlementPlanItem`会提交事务，接入全run原子生成前需提取不提交的私有persist primitive，原generate_only wrapper继续保持原提交规则。新阈值intent与原每日唯一intent分开，按原定义mode核对，两者都由原ledger_requests父锚负责；新SQL view/延迟约束只给正确mode开放对应路径，不能用OR放宽旧申请。原系统actor仍明确为settlement-scheduler，不伪造管理员在线会话。

已有scope结构的新阈值字段必须`omitempty`，旧nil序列化逐字不变。扩展前已用固定零测试密钥及合成固定字段捕获旧generation proof `fb2a39232ef520489963c2269ae13c31ac8058c9299c78cf67478905318817b3`，不是实际授权或秘密。后续改变结构必须维持这一历史格式，并做真实73→74旧记录可读/可生成、无回填验证。
