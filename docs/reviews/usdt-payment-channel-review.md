# USDT 支付通道集成审查

日期：2026-11-13。审查基线：`ecdd3c86d82a462002bd720449a418887360f99b`。

后续实施按 [USDT 支付通道计划](../superpowers/plans/2026-11-13-usdt-payment-channels.md) 进行；实际接口和管理入口见 [当前设计](../design/usdt-custody.md)。以下保留原始审查发现，描述的是上述基线，而非后续实现的当前状态。订单统一入口采用资产页签及服务端通道过滤，避免混合资产金额和分页语义。

## 结论

USDT 应进入统一支付方式和支付通道管理。此前将独立资产账本扩展成独立收款入口，造成业务配置脱节。当前实现包含 USDT 收款服务及兼容接口，但尚未完成统一通道接入。单独移动菜单或追加类型枚举不能解决下面的问题。

本报告是静态源码审查及改造设计，未修改运行代码、未部署、未访问生产或执行支付测试。没有开启主网，也没有新建容器。

## 已确认问题

### P1：兼容下单未遵守现有通道准入

`internal/server/server.go:822` 对 `type=usdt` 提前分流。`internal/server/crypto_compatibility.go:110` 按请求网络或默认网络直接创建订单，不读取 `channel_id` / `subchannel_id`。

普通通道在 `internal/server/provider_policy_routing.go:231` 检查支付方式启停，在 `:354` 检查用户组路由，在 `:493` 和 `:500` 检查运行通道权限及限额。USDT 分支不经过这些检查。兼容入口已有商户签名及部分共享支付策略，并非没有任何验证，但不能因此认为通道权限已生效。

影响：启用 USDT 服务后，管理员原有通道配置不能完整控制新建 USDT 收款；显式指定的错误通道会被忽略。主网开启前应统一此准入边界。

### P1：控制台原币收款与兼容入口的业务策略不一致

`internal/server/crypto_console.go:274` 直接调用 `Crypto.CreateInvoice`。该入口有本人会话、权限、CSRF 及事务内身份复核；`internal/cryptopay/invoices.go:78` 检查网络与商户收款状态。但是没有执行兼容入口中的共享 `CheckPayment` 业务规则，也没有通道授权和用户组规则。

影响：同一商户使用不同收款入口可能得到不同的业务准入结果。需抽取适用于各收款入口的共同策略，并明确原币金额与人民币报价金额各自的限额单位。

### P2：支付目录、收银台、费率及原单归属未统一

- `web/src/pay-types.ts:15`、`internal/backoffice/extended.go:7` 和 `internal/server/pay_type_catalog.go:18` 无 USDT 类型。
- `web/src/parent-channels.ts:149` 不接受 USDT 通道；通道界面无法完成新增、编辑和授权。
- `internal/server/cashier.go:128` 枚举既有支付目录及 provider 通道，未接入 USDT。
- `web/src/group-payment-rates.ts:1` 无 USDT；`internal/cryptopay/invoices.go:142` 使用网络全局 `FeeBPS`，没有使用现有用户组/商户通道费率。
- `internal/cryptopay/model.go:38` 的 Invoice 没有持久通道 ID 和通道配置修订。当前网络、金额及地址会固定，但不能据此追溯统一通道规则。

## 目标结构

| 业务位置 | 调整后职责 |
| --- | --- |
| 支付方式 | 增加 USDT，拥有统一展示名称与新收款开关 |
| 支付通道 | 建立 USDT · TRON（TRC20）、USDT · Ethereum（ERC20）通道，绑定固定网络，管理启停、授权、费率和明确单位的限额 |
| 用户组与商户配置 | 配置可用 USDT 通道与费率继承，禁用、未授权和不存在通道均由服务端拒绝 |
| 收银台及下单接口 | 基于共同准入选择通道；指定网络只能缩小候选范围，不能覆盖已绑定通道的网络 |
| 收款订单 | 统一查看入口，清晰列示报价币种/金额、到账资产/金额、网络、通道及状态 |
| USDT 资金管理 | 保留分链余额、原链退币、结算、收款地址池、归集和对账 |

通道页面按能力展示操作，不能给 USDT 自动附加人民币付款、批量结算、手续费统计或人民币退款操作。收款开关、出款开关、扫描状态、签名服务状态应分别表达，避免用单一“已启用”掩盖依赖未就绪。

## 实施边界

1. 统一业务目录、通道身份、权限及路由后，再按结算资产调用对应执行服务。USDT 继续使用 `cryptopay`。
2. 新单事务内固定通道 ID、通道修订、网络、报价、USDT 金额、费率来源和手续费；重放与回调沿用原单，不因后续配置变化重新计费或换链。
3. 管理界面不能绕过部署总开关。网络服务、签名及广播未授权时，网页启用通道也不能开启主网收付款。
4. 关闭新收款不应停止核对历史地址、已广播交易或已存在的回调。历史订单和历史通道需保持可追溯。
5. RPC 信任配置、合约白名单、资金私钥及独立签名器策略保留在受控部署边界。通道表单不接收资金私钥。
6. 统一订单列表优先使用带资产和网络的只读联合投影。`000199_crypto_custody.up.sql:75` 已禁止同一商户外部订单号同时写入人民币和 USDT 两张订单表，不能通过重复插单来统一显示。
7. 现有 `payment.Provider` 的创建/退款金额没有完整资产与网络信息，`provider_flow.go:204` 和 `provider_flow_operations.go:73` 显式要求 CNY，`store.go:393` 写人民币账本。直接注册 USDT 并复用这条入账路径是不安全的。
8. USDT 继续使用六位精度；TRON 与 Ethereum 余额不互抵，统计不混加人民币和 USDT。链上退款需要原单网络及经审批地址，不能把交易所发币地址当作安全退款地址。

## 改造验收要求

- API、控制台和收银台三种入口，对支付方式关闭、通道关闭、商户禁用、组禁用、越权通道和超过限额给出一致拒绝结果。
- 错误通道 ID、错误网络、通道与网络冲突、未支持子通道必须明确拒绝，不能静默改走默认通道。
- 费率继承、配置修订、并发关闭与创建、原单重放均有回归测试；旧单金额/通道/链/地址不可变化。
- TRON 与 Ethereum 的创建、确认、回调、原链退币及结算仍只在本地模拟验证；人民币余额和分录不受影响。
- 统一订单过滤、分页、详情、统计和手机布局要覆盖混合资产数据，金额单位始终可见。
- 部署总关闭时，所有入口均不能创建主网收款或出款，已关闭能力页面仍可读取历史记录。

上述是待实施与待验收项目，不是本次已通过测试的声明。
