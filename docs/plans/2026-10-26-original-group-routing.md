# 用户组原通道与费率绑定

此152开发设计的“通道0继承默认”及首项顺序假设已被原版代码否定，152明确禁止部署。以同目录2026-10-26-original-group-route-semantics.md的153纠正设计为准：0关闭、-1随机、-4共享组游标顺序、-5数字ID升序首项。以下保留当时设计作为差异调查记录，不能作为兼容性结论。

本地 Pro 的 info 将每种支付方式的 rate 与 channel/type 一并提交；支持默认通道、首个可用通道、指定通道和指定轮询。当前 Go 仅消费 rate，通道目录记录也不等同实际运行通道。必须从实际已加载 Provider 和真实轮询读取选项，禁止用目录自增ID假装运行通道。

边界分为纯配置模型、后台配置验证与运行目录读取端口、已有新单路由用例及界面控件。纯模型不依赖 HTTP/PostgreSQL/支付 SDK：严格检查重复/未知键，精确整数编号/比例，兼容旧 rate-only 形状；正数通道/轮询必须完整声明类型，0继承默认，-5首个可用。用户自定义子通道等尚缺实际配置来源的分支继续独立实现，不归入用户暂缓的其它业务插件，也不添加假选项。

后台写入通过实际运行目录校验，不开放配置文件/凭证读取。运行 Provider 编号、方式/产品和轮询编号均为字符串。配置写入不改变部署写入开关，不扩大商户 allowlist；组通道在已授权范围内选择，仍执行现有风控、金额限制、通道停用和真实资金开关。轮询复用当前策略/配额/计数及原分配事务，不复制一套算法。

原单及已准备 OAuth/小程序材料优先沿用原通道与既有 HMAC 分配，禁止换组或改配置后自动换通道，也不重新计算已生成订单的原手续费。新单读取有效用户组时按固定顺序锁定可能的基础/会员组，锁等待后按数据库 clock_timestamp 重新判断会员期限；未知归属与无可用真实绑定明确失败。配置选择必须在原分配事务中完成，全部外部 I/O 仍在原意图持久化之后。

先完成纯模型正反例和旧费率回归；再接实际目录端口、组写入和新单路由，测试明确通道、轮询、首个可用、显式请求冲突、商户授权、组停用、会员锁等待到期、改组后同号与原退款金额。覆盖普通签名V1/V2、聚合收款、充值及 OAuth/小程序路径，不能只接一个创建入口。业务与安全全部接通后才开放前端通道选择；后续完整前端、双平台 Go/race、PHP互操作、隔离模拟及备份恢复通过才部署。

本设计不在本轮引入动态凭证切换；运行通道仍来自显式受控的已加载配置。通道资料创建/编辑与后续凭证版本管理、默认组0配置和子通道继续按全量整改清单完成。所有原资料仅本地读取，禁止生产访问或真实资金动作。

开发验证补充：会员先锁基础组与会员组再读数据库时钟，等待通道配额后及持久分配前再核对不可变会员截止时间；到期不创建订单路由，不静默切换。新组候选在同一事务内复用原签名停用历史读取，已停用候选排除，无法核实的历史明确失败；原已分配材料和未知结果保持原通道。实际已覆盖V1/V2两方式、聚合收款、充值、网页OAuth两方式、小程序OAuth两方式与启动材料的整条既有正反例。仍须完整固定源码门禁和本地部署，不能把开发专项当作最终验收。类型检查只用 --noEmit；开发过程中误用 -b 产生的260个JS旁文件已逐个核对不属原清单并归档，后续所有测试直接消费TS/Vue源文件。
