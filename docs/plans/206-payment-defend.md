# 206 创建订单人机验证

## 范围和依据

对照本地 Pro 风控设置页的七个原字段和选项，独立实现创建订单验证设置。原加密消费代码不可见；Release 的规则仅作为可核查的参考，不把它的行为宣称为 Pro 的确切实现。保留字段输入原文，未配置时明确关闭。其它业务插件不在本阶段范围。

## 数据与管理接口

迁移 118 新增独立策略、完整性凭据和审计，不回填或改写旧风险策略、旧 MAC、历史订单。读写使用固定字段、持久超级管理员身份、CSRF、指纹比较和事务串行化；错误、损坏或密钥缺失必须关闭访问而非隐式放行。设置页沿用 Pro 的字段、条件显示、确认和冲突重读交互。

## 创建订单边界

验证必须在路由计数、订单和支付尝试创建、第一次上游发送之前执行；配置或授权变更与这些事务之间不能出现绕过窗口。已存在订单的查询、通知和恢复不因新规则失去处理能力。各验证用途使用独立供应商配置，拒绝跨用途重放；不会使用第三方演示验证服务。仅管理设置可用并不代表支付验证已完成：跳转、接口提交、规则统计、挑战和验证的每个分支都需真实本地 HTTP 与数据库测试。

现有路由、订单创建和首发占有分别开启事务。只在 HTTP 入口读取一次策略无法保证并发一致性；把外层锁事务持有到上游响应会占用连接，并可能在单连接池中自我阻塞。拟在各短事务的业务写入前获取策略共享锁并复核授权，策略修改取得同一锁的独占权；首次发送的占有事务提交是本次外部请求的授权边界，提交后释放连接，再执行外部请求。若配置在阶段之间变更，之前已提交的路由或订单事实可能保留，后续首次发送必须被阻断；不得将这种情形表述为全部副作用回滚。OAuth、扫码、小程序、预授权和已有尝试的恢复各有独立生命周期，必须分别证明该模型适用；不得为了复用而允许补发上游请求。

按以下顺序补全，所有切片先以实际 HTTP 和数据库回归证明缺口：

1. 保留原商户签名规范。Release 的浏览器提交会先剥离 `__defend`；只在浏览器提交的兼容分支处理平台验证字段，必须仍验证原签名和平台凭据，不能全局从签名规范中忽略该字段。API 创建接口不得用浏览器凭据绕过。
2. JS 跳转使用不透明、一次性的继续令牌，绑定完整请求、商户、订单号、浏览器、用途、策略指纹和期限；验证前不创建路由、订单或支付尝试。JS 跳转本身不证明用户是真人。
3. 单独实现名单和分组继承／覆盖，并从可信商户关系读取分组，不改旧风险策略的 MAC。对 Pro 加密实现不明的边界保留差异说明。
4. 模式 1 的窗口、状态、舍入与空值需单独定义并验证。Release 的 `status>0` 不等价于当前的已支付状态；不得把缺失历史事实当零或补造证据。Pro 界面和 Release 对空值的说明不同，不能宣称两者等价。
5. Geetest 使用独立用途配置、挑战和全局原生凭据去重；验证网络未知时不得放行或自动续付，不调用原版演示服务。
6. OAuth 和小程序的授权码可能已被消费；保存受保护的原账号和付款人继续证据，验证完成后只恢复同一订单，不能重复交换授权码或重复首发。已存在的未知支付继续仅按原请求查询。

## 验证与部署

先记录真实失败，再运行领域、HTTP、并发和前端测试；用隔离的合成数据、受控验证服务及模拟支付测试，不访问生产或产生真实资金交易。重用现有容器，升级之前备份并验证既有本地预览数据。未获得原加密规则或对应样本的行为，明确保留为待验证差异。
