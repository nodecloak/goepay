# 原支付风控、扫码校验与 Check 对照

本实现只使用本机公开表单、可读 PHP 和合成支付材料。Pro 的 RiskCheckLogic/PaymentService 内核加密，具体规则以源契约中明确标注的可读 Release 证据补充，不把推测写成 Pro 原行为。投诉、进件业务插件仍按用户指示暂缓。没有访问生产、SSH、真实上游或真实资金。

## 配置与消费者

- 25 个全局原字段：24 个首次付款/周期检测字段，另加原拼写 `check_pay_regoin`。值为 `0` 不校验、`1` 不一致禁止、`2` 不一致提示。空值/0 关闭金额与频率门槛；金额使用分整数。买家已有成功实付累计达到阈值才阻止下一笔，本笔可以越过阈值，不偷换成 sum+incoming 硬资金上限。
- 用户组 `config` 单独保存 `pay_block_oversea` 与 `check_pay_regoin`，空串继承；原 UI `_` 哨兵规范化为空串。显式 0 覆盖系统开关，实际生效组由原会员有效期/默认组判定，首次发送最终写等待后再核有效期。原 `info` 支付路由/费率结构没有混入这些字段。
- 全局/用户组配置与处置均须本人持久 super 会话、原 CSRF 和 CAS；组确认指纹包含系统继承状态及原组记录，系统设置变更后旧组确认失效。所有 ID、修订都用 int64 十进制字符串传给前端。
- 首次付款在原订单/attempt 事务内检查 IP、买家、地区及持久风险处置；原 attempt 返回在新准入之前。同一买家/IP 的未决首次发送占并发名额，统计仍明确区分成功与占位；旧查询/回调/已授权 unknown 恢复不会重新准入。
- 默认只信真实 HTTP peer；仅显式可信直连代理及单个覆盖的 X-Real-IP 可以替换。签名 mapi 的 clientip 保留为“商户声明客户 IP”，从不冒称真实网络身份；原 submit 以直达可信 HTTP 客户地址为基准。二者来源独立冻结。

## 扫码中转

可读 Release Plugin::checkpay 与 Payment 的组合证明，这是生成支付材料后的扫码/跳转中转，而不是回调验签。对新出生的支付宝/微信 native、WAP/h5 HTTP(S) 二维码/跳转材料，返回和 QR 图片使用带时限 HMAC 的平台中转地址；私有原材料、原接收账户、原 provider trade 均保留。

扫码时比较出生基准 IP 与当前可信扫码 IP 的省、市。1 拒绝；2 显示反代付提示并提供单独签名的真实继续入口。1 不能通过直接打开继续入口跳过。系统/组配置后续变化不会改写旧出生策略。缺少本地地址库不能启用，运行时库故障/没有可比较省市返回明确 503，不把“校验不了”伪装为一致。原 Release 在缺库/异常时放行，这里按用户要求加固。

中转路径为 `/checkout/{trade}/scan-region` 和 `/scan-region-continue`，沿用现有带用途的 checkout 能力 token。支付状态已确认、原查询、回调和商户 return 都不进入新的地区拒绝流程。未包裹的 HTML、APP、JSAPI、小程序、付款码与预授权材料保持各自原消费者，不能按页面表单标签泛化地区规则。

## Check 与通知

可读四条规则都有真实消费者：IP 连续未付五天封禁、买家成功速度（0 天为永久）、商户低成功率、通道最新 N 笔全未付。观察按原订单时间窗、最新 trade_no 排序；包括已有路由但还没有 provider attempt 的原订单。最后处置/通知/审计写等待后复核真实数据库时钟，观察窗过期会整事务回滚。

子通道集成在独立 184 验证树中：沿 98 原 route/quote/account/birth MAC 恢复子通道命名空间；多账户父通道存在有效子通道时按原分支逐子通道检查，不因一个子账户失败关闭整个父通道。受限子通道仍保留原配置 enabled，选路跳过其新付款，原账户查询/回调继续；只读列表分开显示配置与实际新付款限制。父/子风险、商户人工 pay=0、原账户与 fee/capability 都独立生效，解除风险不会重新开启人工关闭状态。

风险处置是独立 MAC、追加记录与独立审计锚点，避免裸写 pay/enabled。解除必须同时持有原处置和当前风控指纹；旧合法行回退、丢失最新 head、丢失原准入/成功来源、部分/全表丢失都不能悄悄降级为未配置。私有 facts 必须匹配原 writer 的精确 JSON 形状，拒绝大小写 shadow/未知字段；公开 DTO 不包含原 IP、买家标识、私有 proof、密钥、邮箱密文或租约。

两个通知开关都会生成冻结内容的 AEAD 来源、job、一次性领取/结果记录，并经现有 SMTP/管理员消息工厂消费。独立 `GOEPAY_ENABLE_CORE_RISK_NOTICES` 默认关闭；unknown 或丢失原领取/结果证据不会重新发送。子通道通知沿管理员通道路由；成功重放只恢复原结果。

171 集成提供真实 `check` registry 与执行入口，使用相同事务校验原 run MAC/审计、原 token/epoch/lease 和当前 enabled/generation，在所有风险 action/notice/audit 写后再次检查。失败计数为零，不能把已回滚的处置上报成成功。独立 CLI 另需显式 `GOEPAY_ENABLE_CORE_RISK_CHECK=true --once --external-no`；同 key 只恢复原结果，不生成新检查。

## 验证与集成边界

迁移仅使用专属 `000102_core_payment_risk.up.sql`，不占用 103/104/105。实际 Migrate/重复 Migrate 验证旧表所有旧列、旧注册时间及原真实 fee proof 不变，未伪造旧历史。独立 177 树以 175 为基线；184 整合验证树另外保留 98/99/100/101 与原 paid_at 修复。180/185 后续父账户/批量变更不在该整合树内，最终累计合并与全量验收仍由 root 执行。

本地 PG/HTTP、真实 CLI、原 provider 回归、Vue 单元/noEmit、Chromium 1440/375 验证分别保存不可覆盖的失败/成功收据。浏览器使用实际 HTTP 导出的公开合成 DTO；浏览器 mutation 回包用于交互与真实 ApiClient 传输契约验证，不能冒充 PG 提交证明，PG 提交另由真实 HTTP 测试验证。最终测试索引逐项标明这个区别。
