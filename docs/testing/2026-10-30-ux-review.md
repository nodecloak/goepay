# 后台功能与交互合理性复核（2026-10-30）

修复状态（2026-10-31）：下列 7 项问题已完成本地修复及回归，并补齐退款异常回包、管理员原退款核对入口与嵌套设置草稿保护。最终结果见 [修复与验证报告](2026-10-31-ux-fixes.md)。下文保留原审查结论及当时的复现证据；本轮修复尚未部署线上。

结论：当前功能骨架与主要账务约束有合理基础，但不能认定“所有功能和交互都合理”。已确认两项应优先修复的资金操作交互问题，以及五项影响理解、效率或工作成果保留的问题。本轮是审查与诊断，没有修改业务代码或部署。

此前的逐节点测试报告证明页面、接口及指定业务场景能够执行，不是交互设计验收结论。“不溢出”“最终状态正确”和“没有脚本错误”都不能替代对反馈、恢复路径和误操作风险的检查。特别是冻结成功提示的断言在上轮被改为核对最终状态，虽证明资金状态正确，却漏掉了提示被刷新抹掉的交互缺陷。

## 应优先修复

### 1. P1：资金操作反馈和原请求上下文被刷新抹掉

影响：管理员在订单菜单执行冻结、解冻或重新通知，刚出现的成功、失败或结果未知提示会随着详情刷新消失。发生网络未知结果时，原请求号及通知冷却信息也可能被重建；用户难以判断是否完成，更难遵循“保留原请求号重试”的提示。

证据：

- [AdminOrderActionDialog.vue](E:/GOEPAY/web/src/components/AdminOrderActionDialog.vue:256) 在子面板更新后调用 `load()`；[287 行](E:/GOEPAY/web/src/components/AdminOrderActionDialog.vue:287) 的 `v-if="data && !loading"` 在刷新期间卸载子组件。
- [OrderIncomePanel.vue](E:/GOEPAY/web/src/components/OrderIncomePanel.vue:154) 成功或异常均在 `finally` 发出 `updated`，原请求号、错误与成功提示保存在该组件内部。
- [NotificationDeliveryPanel.vue](E:/GOEPAY/web/src/components/NotificationDeliveryPanel.vue:106) 同样在结束时刷新，内部保存的原请求号、未知标志和冷却倒计时随实例丢失。
- 本地 Chromium 已复现：成功冻结后最终冻结状态存在，但成功提示不可见；模拟冻结请求连接中断并让后续详情读取返回 503 后，原冻结 UUID 被新 UUID 替换，未知结果提示消失，页面再次出现“确认冻结收入”。记录为 `.tools/ux211/feedback-reproduction.json`，截图同目录。整个复现使用静态前端与模拟 API，无数据库、生产访问或真实资金。

改法：刷新权威数据时保留操作面板实例；本次操作结果和未决意图放在稳定的父级/请求存储中。未知时继续显示原请求号，提供“查询原操作 / 重试原请求”，不要自动创建新意图。成功提示保留到用户关闭或明确开始下一次操作。

验收：成功、明确拒绝、超时、响应丢失及刷新再次失败都要有明确且持续的反馈；未知时原请求号、金额、目标与冷却状态保持不变。

### 2. P1：退款、提现申请的未知结果缺少原意图恢复流程

影响：请求可能已被服务端接收，但浏览器未收到响应。当前只显示错误并重新开放表单，用户可以改变请求号或取消重开。同一笔部分退款或同一提现意图可能被当作新的业务申请再次提交。服务端对相同请求号的幂等有效，但不能替用户识别更换请求号后的重复意图。

证据：

- [App.vue](E:/GOEPAY/web/src/App.vue:1224) 退款异常后只写入错误并释放 `busy`；[重新打开退款](E:/GOEPAY/web/src/App.vue:1148) 会清空金额并生成新的 `refundExternal`。没有未决退款意图恢复状态。
- [WorkflowPage.vue](E:/GOEPAY/web/src/components/WorkflowPage.vue:572) 结算/站内转账提交异常后只显示错误并恢复 `busy=false`；金额及业务请求号仍可编辑，缺少“核对上次申请”的明确入口。

改法：持久保留本次订单/金额/收款版本/请求号，未知结果期间锁定原意图并提供原单查询和原请求重试。明确拒绝或核对终态后再开放新申请。重新打开同一业务对象时恢复未决操作，而不是直接生成新号。

验收：模拟服务端成功落库但响应丢失，取消重开或刷新后仍能恢复原意图；不能把网络异常直接展示为“确定未提交”。

本项是界面恢复路径的风险，不是已发生重复付款、后端幂等失效或账本不平的证据。

## 需要改善

### 3. P2：“确认收款”入口没有按真实能力显示

影响：支付宝已完成结算、甚至尚未准备出款的已核准记录，都可能显示“确认收款”。点击后才告知没有可用二维码，按钮所承诺的动作与实际能力不一致。

证据：[settlement-list.ts](E:/GOEPAY/web/src/settlement-list.ts:188) 只根据 `approved` 设置 `canInspectPayout`；[SettlementListTable.vue](E:/GOEPAY/web/src/components/SettlementListTable.vue:224) 用相同条件显示确认收款按钮。已有真实本地浏览器快照包含支付宝已完成行仍显示此按钮。服务端只在适用的微信待确认状态提供确认 URL。

改法：使用服务端明确的 `can_confirm_receipt` 等能力字段，仅在可确认时显示“微信确认收款”；其他记录显示实际状态，保留独立的出款详情入口。

### 4. P2：未开放功能展示为英文接口故障

影响：管理端投诉三个入口在开关关闭时仍展示查询、刷新或同步入口，页面显示 `complaint feature disabled`。用户难以区分未开通、无权限和系统故障，容易反复点击。

证据：[menu.ts](E:/GOEPAY/web/src/menu.ts:273) 的功能开关过滤仅作用于商户菜单；[ComplaintsPage.vue](E:/GOEPAY/web/src/components/ComplaintsPage.vue:133) 原样展示接口错误。上一轮桌面和手机均记录了对应 403 及英文提示，详见 `.tools/browser210`。

改法：管理端可以保留配置入口，但应展示中文“交易投诉尚未启用”，说明原因，停用无效业务动作，并提供可用的设置入口。将未启用、缺少插件、没有权限、请求失败分开呈现。

### 5. P2：系统设置刷新或离开会丢失未保存修改

影响：管理员修改多项配置后点击“刷新设置”或离开页面，草稿没有确认提示便消失。

证据：[SettingsPage.vue](E:/GOEPAY/web/src/components/SettingsPage.vue:292) 重新生成配置并覆盖 `values`；[476 行](E:/GOEPAY/web/src/components/SettingsPage.vue:476) 的刷新按钮直接调用 `load()`。当前修改追踪只覆盖当前分类，尚无全部分类的离开保护。

改法：检测全部分类的未保存修改，刷新/离开前提示未保存项数量并确认是否放弃；分类切换继续保留草稿。

### 6. P2：手机订单列表没有优先呈现金额和状态

影响：375px 下首屏每行主要呈现订单号与操作入口，金额和支付状态需要横向滚动。页面没有整体溢出，但用户核对订单与退款对象仍不方便。

证据：`.tools/browser210/screenshots/mobile-merchant-OrderList.png`、`mobile-admin-OrderList.png`；[DataTable.vue](E:/GOEPAY/web/src/components/DataTable.vue:533) 固定右侧操作列，窄屏仍使用桌面宽表。

改法：移动端每行首先展示订单号、金额、支付状态，再呈现操作入口；次要信息折叠到详情，或明确提供表格横向滚动提示。

### 7. P2：商户收款资料技术字段缺少引导和字段级校验

影响：普通商户填写微信 AppID、银行代码时没有来源说明；账号、姓名、AppID 或银行卡格式的不同问题都返回相同错误，用户无法定位。

证据：[SettlementRecipientPanel.vue](E:/GOEPAY/web/src/components/SettlementRecipientPanel.vue:217) 自由输入 AppID/银行代码；[settlement-recipient.ts](E:/GOEPAY/web/src/settlement-recipient.ts:60) 将多种问题合并成“请填写完整且有效的收款资料”。

改法：提供已配置应用及开户银行选项；确需手填时说明来源。将错误绑定到具体字段，提交后聚焦第一个错误。已有转账页的银行选择方式可作为实现参考。

## 应保留的合理设计

- 结算前展示可出账余额、手续费和预计到账金额。
- 结算申请、审核与实际出款各自有状态，收款资料采用版本快照。
- API 退款与手动退款有明确业务区分，后台状态标记说明不会凭标记增加余额。
- 订单删除可恢复，账务依据保留。
- 未知付款结果不直接视为成功，批量付款区分未发送与已发送；部分执行后可以取消仍未发送的项目。
- 服务端权限、本人敏感操作约束、资金授权与幂等机制继续保留。

改进顺序：先处理未决资金意图和结果反馈，再处理入口能力、关闭状态和草稿保护，最后优化手机信息布局及商户字段引导。继续沿用 epay_pro 可识别的菜单与操作习惯，避免在修复交互时改变支付接口或账务规则。
