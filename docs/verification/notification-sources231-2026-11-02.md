## 行为与来源

| 场景 | 可信出生点 | 收件人与防重复规则 |
| --- | --- | --- |
| 商户交易投诉、管理员全部交易投诉 | 签名上游投诉同步首次写入，与原投诉事务一致 | 上游商户单号按平台 `orders.trade_no` 精确匹配。全部单号必须拥有同一商户、对应通道已验证回执和原付款账户；缺失、混合商户或换付款账户只通知管理员。管理员未知归属显式为 NULL。重复同步不补发首次提醒。 |

微信确认模板与映射在来源出生时记录摘要。未启用公众号通知或缺失模板的旧 package 不会因后来配置而重新取得发送机会；claim 不接受不同模板。发送前再次检查商户、原转账待确认状态和当前 job lease。已消费 claim（包括网络结果未知）始终不能重发。

投诉 resync 使用本次强校验结果替换原来的 best-effort owner，清除无法证明的旧归属，避免商户详情及原投诉订阅继续使用错误归属。原 201 投诉 HTTP 订阅与新的邮件、短信、机器人通知保持独立。

## 持久化与约束

- 189 增加不可变 `notification_sources231`，仅存私人事实摘要；具体收款人及消息事实仍位于既有加密通知事件。新出生字段不回填历史资料。
- 189 的 direct 只允许微信确认来源；NULL profile 的 claim 只接受 Wechat、匹配的原始不可变来源、启用商户及有效任务租约。旧 profile claim 的约束保留。
- 190 增加 `complain_all`、`channellimit`，允许这两个全局场景的未知商户为 NULL；独立 `(event_id, job_id)` FK 在商户 NULL 时仍约束任务归属。
- 管理员 mode 3 仅适用于全部投诉短信。最终 schema 保留 `admin_business_mode231`；实际 PostgreSQL INSERT 断言其他场景 mode 3 被该 CHECK 拒绝。
- 既有 merchant/admin 通知完整性检查涵盖新来源、claim 和结果，检查项总数不增加。
