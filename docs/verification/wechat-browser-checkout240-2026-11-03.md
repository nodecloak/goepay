# 微信收银台与二维码居中验收

目标版本 `2026.11.03-240`。本记录描述发布前的实现与验收范围，实际发布结果另存独立回执。

## 支付交互

| 原订单方式 | 电脑端 | 手机端 |
| --- | --- | --- |
| Native 原生扫码 | 显示原支付二维码，轮询本地确认状态 | 保留原二维码和扫码说明 |
| H5 | 显示原订单的带签名继续支付二维码 | 外部浏览器自动进入原 H5 链接；微信内提示通过菜单在浏览器打开 |
| JSAPI | 显示原订单继续支付二维码 | 微信内等待 `WeixinJSBridgeReady` 后调用原签名参数；微信外展示微信打开指引 |
| APP | 显示原订单继续支付二维码 | 保留原应用支付入口，引导回到发起订单的应用 |

Native 的官方流程是展示 `code_url` 二维码，由微信扫一扫完成支付，不能把原扫码订单当作 H5 订单直接跳转。H5 需要来源域名 Referer，且应在微信外浏览器调起。依据：[微信 Native 调起支付](https://pay.wechatpay.cn/doc/v3/merchant/4012791878)、[腾讯 H5 支付常见问题](https://typ.wecard.tencent.com/developers/product/c2b/h5/faq)。已有 H5 会话可能受原付款 IP、时效和商户开通能力约束；页面展示不会重新申请上游会话。

手机继续支付始终使用同一订单、金额、通道、账户、付款方式及存储材料。桌面继续支付二维码编码原收银台的带签名 URL，不新建付款尝试。待微信授权的订单先在电脑展示原订单二维码，手机打开后再建立其自己的 OAuth state/cookie；桌面不预先绑定手机授权。隐藏商品名称的原有设置同样适用。

JSAPI 桥接取消或失败时给出反馈，仅允许用户明确点击继续；重复就绪事件不会自动重试。桥接返回成功后仍等待本地订单确认，最终通过已验签的异步通知和原商户签名返回完成流程。

## 二维码与风险控制

支付宝原版 `alipay_qrcodepc.php` 使用230×230的 mode4内嵌窗口。旧320px窗口配合靠左的230px二维码会产生45px中心偏移；本次以二维码专用230px窗口居中显示，并保持完整静区。微信及同订单继续支付图片使用响应式居中显示。

HTTP 回归覆盖原方法/账户不变、付款尝试不增、不可恢复账户拒绝展示、未支持插件保持手动流程、篡改授权及非可支付状态拒绝二维码。H5 手机跳转使用经过原冻结风险策略处理的材料，保留地区检查中间页；不会直接绕过到存储的上游链接。

## 本地模拟与发布边界

冻结 Go 输入2570个、web输入1012个。实际 Chromium 测试覆盖微信9个场景及支付宝4个场景，验证1280px、375px视口的二维码中心、静区完整性及页面无横向溢出。

微信采用真实 V2 SDK 与本地签名网关、真实 Go 回调处理链路；仅浏览器原生 JSBridge 边界为模拟。5笔合成订单/5次原付款尝试、4次签名回调、9次商户验签返回，上游查单为零。支付宝验证2笔原订单、3次表单提交、2次签名回调及4次验签商户返回。测试仅访问本地 HTTP/TLS 对端，外部网络请求为零，未验证真实 App、手机摄像头扫码或真实资金交易。

最终冻结相关回归324项通过：收银台/地区风险47项、历史账户4项、微信/支付宝实际浏览器各1项、适配器138项、通道配置68项、cmd65项。5项可选跳过不计为通过：3项 PHP 互操作、旧 `TestCheckoutPollRealBrowserLocalProvider`（本次微信/支付宝新浏览器套件均实际执行）、`TestRisk177PinnedOfficialGeoDrivesActualAdmissionAndScan`（未配置其官方离线数据夹具）。这里不声称执行全仓库 `go test ./...`。

现有1010个应用前端输入未改，仅新增微信独立浏览器脚本并修正原支付宝浏览器测试；113个编译后的 SPA 资产原样复用，旧完整 SPA 回执原地引用，未声称本次重跑完整 SPA 测试。

复用已有 PostgreSQL 容器，测试数据库在连接数为零后清理，现有预览保留。生产发布不执行迁移或配置修改，保持158个迁移及现有配置哈希。发布先备份，确认两个写入服务停止并核对33项账务，再切换程序并只读检查服务、资产和原支付材料。不会打开或提交真实付款页进行上线验收，也不会新建容器。
