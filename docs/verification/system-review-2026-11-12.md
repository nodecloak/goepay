# 系统业务与资金安全复审（2026-11-12）

审查基线：`d0064be30f8d44fc5b4ce8b4b3723a120f76ce15`。本报告记录本轮实际发现、修复及验证范围，不将页面可打开等同于业务完成，也不将合成支付等同于真实通道验收。

## 范围与对照方法

对照本地 `epay_pro` 的可读前端、菜单、字段和动作接口，以及 `epay_release` 的可读兼容实现，整理原管理端 54 个入口、商户端 28 个入口，另列 GOEPAY 的 15 个补充入口。每个入口记录字段、操作、前后端代码位置和未证实能力，详见[逐入口对照表](system-review-2026-11-12-page-parity.md)及[可机读清单](system-review-2026-11-12-page-inventory.json)。

后端复审覆盖支付提交、原订单重放、回调验签、商户通知、退款、预授权、分账、转账、结算、账户与会话、管理员权限、敏感配置和迁移。前端检查包含筛选与分页、导出、异步请求竞争、修改/取消/清除/保存、提交锁定、错误反馈及不同屏幕尺寸。

所有涉及资金的测试仅使用本地合成商户、独立测试数据库和支付替身。复用现有 PostgreSQL 容器，每批测试使用独占数据库，确认零活动连接后清理；没有创建新容器。暂缓的外部业务插件不在本轮新增范围。

## 实际修复

| 问题 | 原行为及影响 | 修复后的约束 |
| --- | --- | --- |
| 退款错误来源未核实 | 普通错误码或不确定结果包装可被当作明确退款失败，提前释放冻结资金；合单子退款也受影响 | 只有同一提供方、精确退款提交操作、可信传输和签名证明的明确拒绝才释放资金；未知结果保留原预留款和请求号 |
| 分账错误重新开放发送权 | 不确定的提交、回退、完结、绑定或解绑错误可恢复额度或允许新号再次发送 | 逐操作验证可信拒绝来源；不确定结果继续占用原请求和额度，只核对原号 |
| 预授权错误放宽扣款或解冻 | 未认证的 not-found 被当作未扣款证据；未知扣款错误变为 failed 后可进入解冻 | 冻结、扣款、查询、解冻分别绑定原支付宝操作；未知、取消和超时包装不能取得新资金操作资格 |
| 等待期间撤权仍可写资金 | 请求通过入口检查后等待数据库锁，账户、会话或菜单权限被撤销仍继续；关闭资金口令策略时也缺少事务内复验 | 在业务事务中锁定并复核原调用者、原会话及当前菜单权限；口令策略关闭不绕过身份检查 |
| 管理员敏感操作使用旧权限 | 等待锁或审计期间被降级/注销，仍可能创建、修改、删除管理员或重置安全凭据 | 敏感写入在业务锁后及审计后验证同一事务的原始授权和截止时间；正常自改密码/用户名仍可原子提交 |
| 菜单权限变化未废止旧会话 | 修改权限再改回，原会话或资金授权可能恢复可用 | 新增 `000198_admin_permission_auth_epoch.up.sql`；实际权限变化递增认证版本，不改旧迁移校验和；相同权限保存不递增 |
| 清除 OAuth 密钥后旧值复活 | 加密存储为空或出错时回退旧明文设置，明确清除后仍可启用旧密钥 | 仅确认加密存储从未初始化时允许受约束的旧值迁移；已有空槽、密钥缺失或解密失败均不回退；首次写入保留其他合法旧槽 |
| 旧 OAuth 配置状态与实际登录不一致 | 首次初始化前旧密钥实际有效，后台却显示未配置，清除入口不可达；旧值变更后仍能使用过期版本提交首次修改 | 读取反映有效配置，仅返回布尔状态与带域分离的 HMAC 指纹；首次修改核对同一旧值快照；共享/独占锁协调读取和首次清除，GET 不写库、不返回密钥 |
| Telegram 新凭据被错误禁用 | 仅设置加密机器人 token 仍要求不适用的 appid | Telegram 按启用状态与有效 token 判断；其他提供方仍要求自身 appid |
| 同步返回忽略隐藏商品名 | 异步通知隐藏名称，但收银台或后台生成的同步返回仍带原名称 | V1/V2 的收银台、商户端和管理端统一按通知名称策略签名生成返回链接 |
| 统计筛选与导出错配 | 未执行查询的草稿条件影响分页/刷新/导出，失败或非法日期可能残留旧汇总 | 草稿与已应用条件分离；分页和导出绑定实际结果；旧异步结果不得覆盖新查询，失败清除过期汇总 |
| 保存中仍能改下拉 | 下拉展开后父表单进入 disabled 状态，仍能选择；资源保存期间字段未统一锁定 | disabled 时关闭下拉且拒绝选择，资源字段跟随提交状态锁定 |
| 批量付款导入诊断丢失 | 通用中文错误覆盖服务端行号诊断，无法定位导入错误 | 使用受限的原始服务端诊断生成逐行提示，保留其它错误处理与资金约束 |

退款、分账、预授权、权限撤销和 OAuth 问题均先以本地失败用例复现，再修复并保留绿测证据；未通过降低资金、归属、签名或幂等断言取得通过结果。支付与账务补丁由不同审查者交叉复核。

普通回归、Linux 并发检测及浏览器验收均已完成，结果如下。各套件存在覆盖重叠，不相加为独立测试总数。

| Go 普通回归 | 79 包、454 批，3,219 个根测试通过、43 个有明确条件的跳过；无隐藏子测试跳过 |
| 前端单元与组件 | 2,043/2,043 通过，零失败、零跳过；类型检查与 Vite 构建通过 |
| 浏览器交互 | 748/748 通过，零失败、跳过、flaky；覆盖桌面及窄屏 |
| 真实本地 API 业务流程 | 19 个文件、52/52 通过；每文件执行 33 项账务与业务核对，全部为零异常 |
| 独立补充根测试 | 15/15 项 opt-in 与 4/4 项支付页浏览器通过，最终源码和数据库清理已核对；主批次对应跳过不改记通过 |

| 支持检查 | `go vet`、Windows/Linux 构建、SDK 19 项、文档工具 2 项通过；OpenAPI 315 路径、386 操作，生成内容无漂移 |
| Linux race | 6 个包、36 批、256/256 个根测试通过，零失败、零跳过、无数据竞争；不表示 3,262 项全部执行了 race |

43 个主批次跳过中，19 个有独立 opt-in 验证；另 16 个 PHP 互操作测试因缺少经过验证的受限运行时未执行，8 个显式预览/语料/样本导出工具未执行。这些未执行项不算通过。

普通回归采用可审计的分包汇总：未受影响包保留原路径的成功回执，整个 `tests/contract` 及剩余 `tests/interop` 在修正夹具后重跑（342 通过、3 跳过）。四个修改文件均为 `tests/contract/*_test.go`，不编译进其他包或生产程序；保存了原/后完整字节、完整差异和 SHA，生产源码未改变。汇总逐项核对全部 3,262 个根测试的唯一覆盖、原始日志、包结束、零连接清理及源码输入；旧失败包的任何结果均不纳入新成功计数，旧整套任务仍保留未完成状态。

夹具修正没有降低断言：支付宝本地 TLS 转发保留原逻辑请求与真实 TLS 响应；预授权与退款的正向可信拒绝场景改用本地 TLS，RSA/MD5 验签、资金预留、原请求重放及单连接约束均保留。另修正旧邮件频率脚本对已删除按钮的引用，并独立复现 Chromium 整分钟时间规范化后，使用等价的分钟精度测试计划任务；原保存、取消和持久化核对保留。

静态浏览器服务器的 3 次空闲连接重置均有待响应数为零的记录；3 次未模拟只读查询返回 503，仅作为诊断保留，不冒充 API 成功。真实 API 依据独立本地业务测试。早期失败、中断及重跑各用新目录，原始证据保存在本地 `.tools/system-review/`，不覆盖或改写为通过。

## 部署与兼容影响

新迁移仅扩展已有认证版本触发函数，升级本身不修改原账户、会话、余额或业务记录；之后实际修改菜单权限会使该账号旧会话失效，需要重新登录。前后端发布应使用同一轮验证后的源码和静态资产，保留原配置与可回退程序链接。

资金结果判定更严格：没有足够可信证据的失败保持 `unknown`，需要按原请求查询或核对，不应通过新请求号绕过。该约束用于防止重复付款、重复退款或提前释放资金，不是将未知结果伪装成成功。

## 证据边界

- 原版部分 PHP 后端经 Swoole Loader 加密。本轮没有解密或执行这些控制器，因此无法证明内部事务、异常分支和并发行为逐行等价；菜单、字段和公开接口的对应关系独立记录。
- 没有发起真实付款、退款、分账、转账或结算；没有测试真实手机支付 App、实体打印、短信邮件送达及暂缓外部插件。模拟结果不代表这些外部服务已经开通或联调完成。
- 自动化覆盖是特定输入和状态组合的证据，不是系统永远无缺陷的保证。失败、跳过、未完成和不可核实项均应单独列明，不能用总通过数掩盖。
